Lesson 62 — Design systems & component libraries

A design system is shared language between design and engineering: tokens, components, patterns and rules that make products consistent and fast to build. As a developer you'll consume one, and eventually build one.

Layers of a design system

  1. Foundations / tokens: color, typography, spacing, radius, shadow, motion, breakpoints. Single source of truth (JSON → CSS variables / Tailwind theme / iOS / Android).
  2. Primitives: unstyled or minimally styled accessible building blocks (Dialog, Popover, Tabs, Menu).
  3. Components: Button, Input, Select, Card, Toast, Table, with variants, sizes and states.
  4. Patterns: forms, empty states, navigation, data tables, onboarding flows.
  5. Guidelines & docs: usage, do/don't, accessibility notes, content style.

Tokens that scale: theming with semantic names

Tooling: Style Dictionary or Tokens Studio transform tokens to platform outputs; Figma Variables mirror them for designers. Use OKLCH to generate perceptually even color scales and check contrast automatically in CI.

Headless primitives: accessibility for free

Building a correct combobox, dialog or menu (focus management, keyboard, ARIA, screen readers, touch) takes weeks. Use headless libraries that implement behavior and leave styling to you: Radix UI, React Aria (Adobe), Headless UI, Ark UI, Base UI, Ariakit.

Designing component APIs

  • Small, composable, predictable. Prefer composition (<Card><Card.Header/><Card.Body/></Card>) over giant prop lists (headerTitle, headerIcon, bodyText…).
  • Variants as data (variant, size, tone) with sensible defaults; limit combinations to what design supports.
  • Forward everything native: accept className, ref, ...rest so consumers can attach aria-*, data-*, events.
  • Controlled and uncontrolled support (value/onChange and defaultValue).
  • Polymorphism with asChild (Radix Slot) or as prop for rendering as link vs button.
  • Accessibility built in, not optional: labels required by types, focus rings, ARIA states, keyboard behavior, reduced motion.
  • Don't leak implementation: stable public API, deprecate before removing, semantic versioning, changelog (Changesets).

Documenting and testing components

  • Storybook documents every state, enables interaction tests, accessibility checks (addon-a11y) and visual regression (Chromatic, Playwright snapshots).
  • Test the matrix: variants × states × themes × reduced motion × RTL × zoom.
  • Publish as an internal npm package (tsup/Vite library mode), tree-shakeable ESM, typed, with peer dependencies on React.

Design-to-code workflow

  1. Designers and engineers agree on tokens and component names first.
  2. Inspect designs in Figma Dev Mode; implement with tokens, never hard-coded values.
  3. Review in Storybook with design before merging; track adoption and detach counts.
  4. Version, document, and treat the system as a product with a roadmap and support channel.

Exercises

  1. Create a token file (primitives + semantic), generate CSS variables with Style Dictionary, and theme an app with light, dark and one brand theme.
  2. Build Button, Input, Select (with Radix), Dialog, Toast and Tabs with variants, states, full keyboard and screen reader support. Document each in Storybook with a11y addon.
  3. Add Playwright visual regression tests for every story in light and dark themes.
  4. Install shadcn/ui in a project, then customize a component deeply to match a brand. List what you had to own afterwards.
  5. Package your components as an npm library with Changesets and consume it from a second app in a monorepo.
  6. Audit a public design system (e.g., GOV.UK, Primer, Carbon) and write a short critique of its tokens and one component's API.

Checkpoint

Why have semantic tokens on top of primitive tokens?Components reference intent (--action), so a theme change remaps one layer without touching component code or guessing which blue to use where.
Why use headless primitives?They encode hard-to-get-right accessibility and interaction behavior (focus, keyboard, ARIA) once, while leaving visual design entirely to you.
