Lesson 49 — Runtime internals: memory, GC, event loop & profiling

Mastery means understanding what the engine does with your code: where values live, when memory is freed, and how work is scheduled. This lets you diagnose leaks, jank and "impossible" bugs.

How the engine runs your code

  1. Parse source into an AST (lazily for functions not yet called).
  2. Interpret bytecode (V8's Ignition) and collect type feedback.
  3. JIT compile hot functions into optimized machine code (TurboFan / Maglev). Optimizations assume stable types; if you break the assumption, the engine deoptimizes.

Practical consequences: keep object shapes consistent (create properties in the same order in constructors/literals, don't add or delete properties later), keep function arguments type-stable, avoid mixing types in arrays, and prefer typed arrays for numeric data. Don't micro-optimize before measuring; the engine is smart.

Memory: stack, heap and references

  • Primitives (numbers, booleans, small strings) are copied by value. Objects live on the heap, and variables hold references.
  • Garbage collection frees objects that are unreachable from "roots" (globals, the call stack, active closures). It uses generational collection: new objects in a young generation (frequent, fast sweeps), survivors promoted to the old generation (rarer, slower).
  • You don't free memory; you stop referencing things. A "leak" is memory that is still reachable but no longer needed.

Common leaks

Finding leaks with DevTools

  1. Memory panel → Heap snapshot. Take one, perform the suspect action (open and close a modal) 10 times, force GC (trash icon), take another.
  2. Compare snapshots (Comparison view): look for objects whose count keeps growing (Detached HTMLDivElement, closures, arrays).
  3. Click an object → Retainers panel shows the chain keeping it alive. The first non-weak path from a GC root is your bug.
  4. Performance panel with "Memory" checked shows a sawtooth for healthy usage; a rising baseline suggests a leak.
  5. performance.memory (Chrome-only, coarse) and performance.measureUserAgentSpecificMemory() for rough in-code checks.

The event loop in full

One thread runs JavaScript. The loop repeats: run one macrotask (script, event callback, setTimeout), then drain the microtask queue (promise reactions, queueMicrotask, MutationObserver), then possibly render (style → layout → paint, with requestAnimationFrame callbacks first), then the next task.

StarvationA microtask that keeps queuing microtasks (function f(){ Promise.resolve().then(f) }) never lets the browser render or handle input, freezing the page just like an infinite loop.
  • rAF runs before paint, once per frame: use it for visual updates. Idle callbacks run when the browser has spare time.
  • setTimeout(fn, 0) isn't instant: nested timers clamp to ≥ 4 ms and background tabs throttle to ≥ 1 s.
  • Long tasks (>50 ms) hurt INP. Break them up, yield with scheduler.yield(), or move to a Worker.

Profiling workflow

  1. Reproduce the slowness reliably; throttle CPU (4–6×) to exaggerate.
  2. DevTools → Performance → record. Read the flame chart: wide bars are expensive, red corners are long tasks. Bottom-up and Call tree tabs show where time goes.
  3. Identify the category: scripting, layout (forced reflows), paint, GC, or network.
  4. Fix the biggest cost first. Re-measure. Stop when you hit the goal.
  5. performance.mark/measure and console.time instrument your own code; the User Timing track shows them in the trace.

Data structures and memory in practice

  • Typed arrays (Float32Array) are compact and fast for numeric data (and required by WebGL/Three.js buffers).
  • Avoid creating millions of tiny objects per frame; reuse objects (object pools) in loops, games and animation.
  • Strings: concatenation in loops is fine in modern engines; very large strings and repeated slice can retain big parents. Use arrays + join for huge builds.
  • structuredClone deep-copies; Transferable objects (ArrayBuffer, OffscreenCanvas) move to Workers without copying.
