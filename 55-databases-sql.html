Lesson 55 — Databases & SQL

Almost every real application is a user interface over a database. SQL is more than 50 years old and still the most valuable data skill you can learn. Practice below with a real SQLite database running in your browser.

Relational model

  • Data lives in tables (rows × columns) with a defined schema. A primary key uniquely identifies a row; a foreign key references another table's row, linking them.
  • Normalize: store each fact once (users in users, not repeated in every order) and join when reading.
  • ACID transactions: Atomic (all or nothing), Consistent, Isolated, Durable. Wrap multi-step changes (transfer money) in a transaction.
  • Constraints (NOT NULL, UNIQUE, CHECK, foreign keys) make bad data impossible. Put integrity in the database, not just in app code.

Schema design: one-to-many and many-to-many

  • Pick types carefully: money as integer cents or NUMERIC, never float; timestamps as TIMESTAMPTZ (UTC); ids as BIGINT or UUIDv7.
  • Migrations: version-control schema changes (Prisma Migrate, Drizzle Kit, Flyway). Never edit production by hand.
  • Soft delete (deleted_at) vs real delete: decide deliberately; GDPR may require real deletion.

Indexes and performance

An index is a sorted structure (usually a B-tree) letting the database find rows without scanning the whole table: reads get much faster, writes slightly slower, and storage grows.

  • Index columns used in WHERE, JOIN and ORDER BY; composite index column order matters (leftmost prefix).
  • The N+1 problem: fetching a list then querying once per item (101 queries for 100 posts). Fix with a join, IN (…), or ORM eager loading.
  • Always paginate; prefer keyset pagination (WHERE id < $last ORDER BY id DESC LIMIT 20) over large OFFSET.
  • Use connection pooling (PgBouncer, built-in pools) because connections are expensive.

NoSQL in depth: documents, key-value and when to use them

"NoSQL" means several different designs. The big shift: you model data around your queries (access patterns) instead of normalizing first, and you often trade joins and strict schemas for flexibility and horizontal scale.

Embed or reference?

In a document database, data that is read together is embedded in one document (fast, one read, atomic update). Data that is large, shared or unbounded is referenced by id (like a foreign key, but joined in your code or with $lookup).

SQL vs NoSQL: choosing

  • Choose SQL when data is relational, you need transactions across entities, ad-hoc queries and reporting, or you aren't sure of your access patterns yet.
  • Choose document/key-value when records are self-contained, shapes vary, access patterns are known and simple, or you need very high scale or a managed serverless store.
  • Mixed ("polyglot") is normal: Postgres as the source of truth, Redis for cache/queues, a search engine for text. Postgres JSONB columns also give you document flexibility inside SQL.
  • NoSQL traps: duplicated data that drifts out of sync, unbounded arrays inside documents, missing indexes, and "schemaless" turning into undocumented schemas. Validate and version your document shapes.
