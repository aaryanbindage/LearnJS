Errors, debugging & saving data

Every program has bugs, and every program meets bad input. This lesson is about handling errors on purpose, finding bugs quickly with the browser's debugger, and saving data so it's still there after the page reloads.

In this lesson you will

  • Throw your own errors, and catch errors with try/catch/finally.
  • Know the common error types and what each one usually means.
  • Debug with console methods and the browser's DevTools debugger.
  • Save data in the browser with localStorage and JSON.
  • Type errors and stored data safely in TypeScript.

About 50 minutes, plus time to practise in DevTools.

Errors: the three kinds of problem

  1. Syntax errors: the code isn't valid JavaScript (a missing bracket). Nothing runs. The editor's red squiggles show you where.
  2. Runtime errors: the code is valid but something goes wrong while it runs (using a property of undefined). The program stops at that line.
  3. Logic errors (bugs): no error message at all, but the result is wrong. The hardest kind. Debugging and tests are your tools here.

Runtime errors have a type that hints at the cause:

ErrorUsually means
ReferenceErrorA name that doesn't exist: typo, or used before it was created.
TypeErrorUsing a value the wrong way: calling something that isn't a function, or using .x on undefined/null.
SyntaxErrorInvalid code, or invalid JSON passed to JSON.parse.
RangeErrorA number outside the allowed range, or a function calling itself forever.

Throwing your own errors

When your function receives something it can't sensibly handle, the right move is often to stop with a clear message, rather than carry on and produce nonsense. throw does that:

new Error("message") creates an error object; throw stops the function and sends the error up to whoever called it, and so on up, until something catches it, or the program stops.

Catching errors: try / catch / finally

You met try/catch in the async lesson. Here it is properly:

  • try { }: run this code.
  • catch (error) { }: if anything inside try throws, jump here. error is the thrown error.
  • finally { } (optional): runs at the end either way. Good for clean-up, like hiding a loading spinner.
When to catchCatch errors where you can do something useful: show a message to the user, try again, or use a fallback. Don't wrap everything in try/catch "just in case" and ignore the error. A silently swallowed error is much harder to debug than a loud crash.

Debugging

Reading a stack trace

In your browser's DevTools console, an error comes with a stack trace: the list of function calls that led to it, most recent first. Each line names a function, a file and a line number. Start at the top line in your code and work down.

The debugger: pausing your code

For tricky bugs, pausing the program and looking around is far quicker than adding console.logs. Every browser has a debugger built in. Try this on your own computer:

  1. Make an HTML page with a script, open it in Chrome or Firefox, and press F12 to open DevTools.
  2. Go to the Sources tab (Firefox: Debugger) and open your script file.
  3. Click a line number to set a breakpoint (a blue marker). Then do whatever runs that line (reload, or click your button).
  4. The program pauses on that line. Hover over any variable to see its value. The right-hand panel shows all variables in scope and the call stack.
  5. Use the step buttons: Step over (run this line, go to the next), Step into (go inside the function being called), Resume (continue to the next breakpoint).

You can also put the word debugger; in your code, which pauses there whenever DevTools is open.

A debugging method that always works
  1. Reproduce: find exact steps that cause the bug every time.
  2. Read the error message and stack trace slowly.
  3. Check your assumptions: log or inspect the values just before things go wrong. Is that variable really what you think it is?
  4. Narrow down: comment out half the code; does the bug remain? Repeat.
  5. Fix, then re-test the original steps.
And if you're stuck for more than 20 minutes, explain the problem out loud, line by line, to someone (or a rubber duck). It works surprisingly often.

Saving data in the browser

All your variables vanish when the page reloads. To keep data, the simplest tool is localStorage: a small store of text, kept in the browser for that website, that survives reloads and restarts.

Common mistakes
  • Empty catch blocks that hide real bugs.
  • Saving objects without JSON.stringify: you get the useless string "[object Object]".
  • Forgetting getItem returns null when nothing is saved.
  • Debugging by guessing: change one thing at a time, and check your assumptions.

Recap

  • throw new Error("message") stops with a clear error. try/catch/finally handles errors where you can do something useful.
  • Error types hint at causes: ReferenceError (unknown name), TypeError (wrong kind of value), SyntaxError, RangeError.
  • Debug with console.log({ x }), stack traces, and breakpoints in DevTools.
  • localStorage stores strings per site. Use JSON.stringify/JSON.parse, handle null and errors.
  • TypeScript: catch (err) is unknown; always-throwing functions return never; type parsed JSON explicitly.

Check your understanding

When does the finally block run?Always, after try (and catch if there was an error), whether or not an error happened.
Why do you need JSON.stringify with localStorage?localStorage only stores strings. JSON.stringify turns objects and arrays into a string; JSON.parse turns it back.
Why is the error in catch (err) typed unknown?JavaScript lets you throw any value, not just Error objects, so TypeScript can't assume what it is.
