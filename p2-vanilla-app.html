Weather & to-do app (TypeScript)

Time to build something real, on your own computer, in TypeScript, with no framework. You'll make a small dashboard with a to-do list that remembers its items, and a weather panel that loads live forecasts. It uses everything from Parts 3 and 4. It's broken into small milestones, so build and commit one at a time.

What you'll practise

  • Types for your data, and functions that update it.
  • DOM rendering, events, forms and event delegation.
  • Saving to localStorage.
  • Fetching from a real API with loading and error states.
  • Modules, a Vite TypeScript project, Git and Vitest.

Expect a few evenings. Getting stuck is part of it: re-read the relevant lesson, use the debugger, and keep going.

Milestone 0: set up

  1. Create a project: npm create vite@latest dashboard -- --template vanilla-ts, then cd dashboard, npm install, npm run dev.
  2. Delete the demo code in src/main.ts and src/style.css, and the counter file.
  3. In tsconfig.json, make sure "strict": true is on.
  4. git init, then commit: "Set up project".

Milestone 1: the to-do types and logic

Start with no DOM at all: just data and functions. Write them in types.ts and todos.ts. Every function takes the current list and returns a new list (like in the Destructuring & spread lesson), never changing the old one.

Milestone 2: show the list

Add the HTML to index.html, then write a render() function in main.ts that rebuilds the list from the data. Remember the pattern from the Events lesson: data → render → page.

Checklist for this milestone:

  • Find each element once, at the top of main.ts, and throw a clear error if it's missing (see the Events lesson's get helper, or use instanceof).
  • Keep the state in two variables: let todos: Todo[] and let filter: Filter.
  • render() clears the list and creates one <li> per visible to-do, using textContent (never innerHTML for user text), and updates the count ("3 left").

Commit.

Milestone 3: make it interactive

  • The form's submit event adds a to-do (remember preventDefault()).
  • One click listener on the list handles both toggling and deleting (event delegation with closest("li") and dataset.id).
  • One click listener on #filters changes the filter. Highlight the active filter button.
  • After every change: update the variable, then call render().

Commit.

Milestone 4: remember the list

Write storage.ts with load<T>(key, fallback) and save(key, value) from the Errors & storage lesson. Load the to-dos when the app starts, and save them at the end of render(). Reload the page: your to-dos should still be there. Commit.

Milestone 5: tests

Install Vitest (npm install -D vitest, add "test": "vitest" to the scripts) and write todos.test.ts. Aim for at least 8 tests. Ideas:

  • addTodo adds an item, trims spaces, ignores empty text, and gives unique ids.
  • addTodo and toggleTodo don't change the original array.
  • toggleTodo only changes the matching item.
  • visibleTodos returns the right items for each filter.

Because all the logic is in pure functions with no DOM, these tests are short and easy. That's the payoff for Milestone 1's design. Commit.

Milestone 6: the weather panel

We'll use Open-Meteo, a free weather API that needs no account or key. It takes two requests: first look up the city's coordinates, then get the forecast for those coordinates. Run this to see the data:

Notice how weatherFor converts the API's data into our own Weather type. The rest of your app only ever sees the tidy type, so if the API changes, only this function needs updating.

Put this in weather.ts, then build the panel:

  • A form with a city input. On submit, call weatherFor.
  • Model the panel's state as a discriminated union, and render each state: { status: "idle" } | { status: "loading" } | { status: "error"; message: string } | { status: "done"; weather: Weather }.
  • Save the last city searched, and load its weather on start-up.

Commit, and push to GitHub.

Stretch goals

Pick any that sound fun. Each one is a chance to look something up and learn on your own, which is a big part of being a developer.

  • Edit in place: double-click a to-do to edit its text.
  • "Clear completed" button, and a "mark all done" checkbox.
  • Accessibility: make everything work with the keyboard only, and announce changes to screen readers with an aria-live region (see the HTML forms & accessibility lesson).
  • Search as you type for the weather, waiting until the user pauses typing (look up "debounce"), and ignoring out-of-date responses (look up AbortController).
  • A chart of the week's temperatures drawn on a <canvas>.
  • Publish it with npm run build and GitHub Pages or Netlify.

Self-review checklist

You're ready for React when you can say yes to these:

Show the checklist
  • npx tsc --noEmit shows no errors, with strict on, and there's no any in your code.
  • User text is only ever added with textContent.
  • The weather panel shows a loading message and a friendly error (try a made-up city, and try with Wi-Fi off).
  • All to-do logic is in pure functions, and the tests pass.
  • Reloading the page keeps your to-dos and last city.
  • You can explain every line of your code to someone else.

In React (next part), you'll find that render(), the state variables and the event wiring are done for you. Because you've built them by hand, you'll understand what React is doing.
