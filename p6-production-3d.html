Project 6 — A production 3D experience

Ship a polished, performant, accessible 3D web application, the kind you'd put at the top of a portfolio. It must run well on a mid-range phone, degrade gracefully, load fast, and have real architecture behind it.

Choose one brief

  • Product configurator: a customizable object (sneaker, chair, watch): materials, colors, parts, camera presets, price summary, share link encoding the configuration in the URL, AR "view in your room" where supported.
  • Browser game: a complete small 3D game (arena shooter, racer, puzzle platformer) with physics, enemies/obstacles, scoring, menus, save data, audio, gamepad + touch support.
  • Interactive story / data world: scroll- or exploration-driven 3D narrative or visualization of a real dataset (city, galaxy, climate), with a 2D accessible equivalent of the information.
  • Multiplayer playground: shared 3D space with presence, chat or simple interactions using “Real-time: WebSockets & multiplayer state” techniques.

Requirements

Technical

  1. React + R3F (or Three.js with a clean module structure), TypeScript strict, Vite or Next.js. State in a small store; no frame-rate data in React state.
  2. Custom visual identity: at least one custom shader or patched material, a cohesive lighting setup, and tasteful post-processing with a quality toggle.
  3. Assets: all models optimized (glTF + Draco/Meshopt, KTX2 textures), documented licenses, a loading screen with real progress, lazy loading for non-critical assets.
  4. Physics or simulation or a procedural/GPU-driven element (instancing, compute, noise generation).
  5. Fixed-timestep logic where simulation matters; unit tests for pure logic (math, game rules, configurators' pricing).

Performance targets

  1. 60 fps on a mid-range phone (or a stable 30 with adaptive quality) and 144 on desktop where possible. Draw calls < 150, initial download < 5 MB (excluding lazy assets), first meaningful content (HTML UI) < 2 s on 4G.
  2. Adaptive quality via PerformanceMonitor/GPU tiers; DPR capped; shadows and post FX scale down automatically.
  3. No memory growth over a 10-minute session (verify with heap snapshots and renderer.info).

Experience & accessibility

  1. Works with mouse, touch and keyboard (gamepad/XR optional bonus). On-screen controls for touch; remappable or documented keys.
  2. Real HTML for all text/UI; keyboard-accessible menus; descriptive text alternatives for the 3D content; prefers-reduced-motion mode; audio mute and captions for important cues.
  3. Graceful fallbacks: no WebGL → static fallback with a message; low-power → simplified scene.
  4. Sound design: spatial audio and UI sounds, with user gesture start and a persisted volume setting.

Delivery

  1. Deployed to a public HTTPS URL on a CDN with correct caching (immutable hashed assets, Content-Encoding brotli, .glb and .ktx2 served with proper MIME types and long cache lifetimes).
  2. CI: lint, typecheck, unit tests, build, Playwright smoke test (page loads, canvas renders, no console errors, a key interaction works) and a size budget check.
  3. README with GIF/video demo, architecture diagram (scene graph, stores, systems), performance numbers before/after optimization, asset credits, and "what I'd do next".
  4. Analytics for load time/FPS buckets and error reporting (Sentry) to learn from real devices.

Milestones (≈ 3 weeks)

  1. Week 1: concept, moodboard, greybox prototype of core interaction with placeholder shapes; performance budget written down; architecture and stores.
  2. Week 2: real assets in the pipeline, materials/shaders, lighting, UI and audio, input on all devices; first deployment.
  3. Week 3: optimization on a real phone, accessibility and fallbacks, tests/CI, polish (transitions, loading, feedback), README, demo video, peer playtest feedback applied.

Self-review

Before you call it done
  • Did I test on a real mid-range phone and a throttled CPU?
  • Can someone play or configure using only a keyboard or only touch?
  • Is there a measured before/after for at least three optimizations?
  • What happens on a 3G connection, with WebGL disabled, and after 10 minutes of play?
  • Could a teammate understand and extend the codebase from the README alone?
