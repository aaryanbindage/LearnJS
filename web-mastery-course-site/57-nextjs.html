Lesson 57 — Next.js: SSR, SSG & Server Components

So far your React apps ran entirely in the browser (client-side rendering). Production sites often render on the server for faster first paint, better SEO and direct data access. Next.js is the most widely used full-stack React framework. Alternatives with similar ideas: React Router (framework mode), Remix, TanStack Start, Astro.

Fast-moving ecosystemNext.js and React evolve quickly. The concepts here (rendering strategies, server vs client components, caching) are stable, but exact APIs, config flags and caching defaults change between versions. Always check nextjs.org/docs for your installed version.

Rendering strategies

StrategyWhen HTML is madeGood for
CSR client-sideIn the browser, after JS loadsDashboards behind login, highly interactive apps
SSG static generationAt build timeMarketing pages, docs, blogs; fastest and cheapest (CDN)
SSR server renderingOn each requestPersonalized or always-fresh pages with SEO needs
ISR incremental regenerationStatic, regenerated in the background every N seconds or on demandCatalogs, news: static speed with fresh-enough data
StreamingShell first, slow parts stream in via SuspensePages mixing fast and slow data

Hydration: the browser receives HTML, shows it immediately, then React attaches event handlers to it. Mismatches between server and client output cause hydration errors (e.g. rendering Date.now() or Math.random() directly).

Setup and the App Router

File-system routing: folders define URL segments; special files (page, layout, loading, error, route) define behavior. middleware.ts (renamed proxy in newer versions) runs before requests for redirects, auth gates and rewrites.

Server Components (the big idea)

In the App Router every component is a Server Component by default. It runs only on the server, ships zero JavaScript to the browser, and can be async: read databases, call internal services, use secrets directly, no API layer needed.

Client Components

Add "use client" at the top of a file for components that need state, effects, event handlers, browser APIs, or libraries that depend on them (including Three.js/R3F canvases). They are still pre-rendered on the server but also hydrated in the browser.

Server ComponentClient Component
async/await, DB, secrets, file systemuseState, useEffect, event handlers
No JS shipped, no hooks, no browser APIsRuns on server (SSR) and client; adds to the JS bundle
Can render Client ComponentsCan't import Server Components (but can receive them as children)
Rule of thumbPush "use client" as far down the tree as possible: make small interactive leaves client components and keep layouts and data-fetching on the server. Props passed from server to client must be serializable (no functions, class instances).

Data fetching, streaming and caching

  • Caching has several layers (request memoization, data cache, full-route cache, client router cache), and the defaults changed across Next.js versions. Learn the current model from the docs; configure per fetch/route (revalidate, cache: "no-store", tags with revalidateTag/revalidatePath).
  • Per-request personalized pages are dynamic (reading cookies/headers/searchParams opts into dynamic rendering).
  • Prefer fetching on the server in components; use TanStack Query on the client for interactive, frequently updating data.

Deploying

  • Vercel (made by the Next.js team): zero-config. Self-host with next build && next start on Node, or Docker (output: "standalone"); Cloudflare, Netlify and others via adapters.
  • Pick the right runtime per route: Node (full APIs) vs Edge (fast, limited APIs).
  • Set environment variables per environment; only NEXT_PUBLIC_* reach the browser.

When not to use Next.js

  • Pure client apps behind login with no SEO needs: Vite + React Router is simpler and cheaper to run.
  • Content-heavy, mostly static sites: Astro ships far less JavaScript.
  • If you don't want framework lock-in or complexity: keep your API separate (Fastify/Hono) and a thin frontend.

Checkpoint

Why are Server Components good for performance?They render on the server and send only HTML/RSC payload, shipping no component JavaScript to the browser, so less code to download, parse and hydrate.
Can a Client Component import a Server Component?No (it would pull server code into the bundle). Instead pass the Server Component as children or a prop from a Server Component parent.
