Lesson 24 — State & events

State is data that changes over time and that the UI depends on. It's the heart of React.

useState

  • Calling the setter schedules a re-render; the component function runs again and useState returns the new value.
  • Normal variables don't persist or trigger re-renders. State does.
  • Hooks rules: call hooks only at the top level of a component (not in loops, conditions or nested functions), and only from components or custom hooks.

RuleWhen the next state depends on the previous, use the updater form: setX(prev => …).

Objects and arrays: never mutate

React compares state by reference. Mutating in place means React sees "the same object" and may skip updating. Always create new objects/arrays (spread, map, filter), exactly as in Lesson 13.

Events

  • Handlers are camelCase props: onClick, onChange, onSubmit, onKeyDown, onMouseEnter…
  • Pass a function, don't call it: onClick={handle} or onClick={() => handle(id)}, never onClick={handle(id)}.
  • The event object is a synthetic wrapper with the usual preventDefault(), target, stopPropagation().

Controlled inputs

A controlled input gets its value from state and updates state on every change, so React is the single source of truth.

Lifting state up

When two components need the same data, move the state to their closest common parent and pass it down as props (plus a setter callback).

Principles for state

  1. Minimal: store the least data; compute everything else during render (derived values like totals, filtered lists).
  2. No duplication: one source of truth. Store an id, not a copy of the object.
  3. No contradictions: prefer one status ("idle" | "loading" | "error" | "success") over several booleans.
  4. Keep state local until multiple components need it.
  5. Lazy initial state for costly work: useState(() => loadFromStorage()).
  6. Reset state by changing a component's key.
