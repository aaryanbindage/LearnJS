Lesson 28 — Context & global state

Passing props through ten layers ("prop drilling") is painful. Context lets distant components share values; dedicated stores handle the harder cases.

Context

Performance caveatEvery component that calls useContext(X) re-renders whenever the Provider's value changes (by reference). Memoize the value, and split frequently-changing data into separate contexts. Context is great for low-frequency data: theme, locale, auth user. It's a poor fit for rapidly changing state.

Context + reducer = a small global store

When to reach for a state library

Kind of stateBest tool
Local UI state (open/closed, input text)useState in the component
Shared between a few nearby componentsLift state up
Low-frequency app-wide (theme, user, locale)Context
Server data (lists, details, caching)TanStack Query / SWR / framework loaders
Complex client state, frequent updatesZustand (simple), Redux Toolkit (large teams), Jotai
URL-representable state (filters, page, tab)The URL (search params)

This matters later: in React Three Fiber, a Zustand store lets 3D objects and UI share state without re-rendering the whole scene 60 times a second.

Exercises

  1. Add a ThemeProvider to your app that also persists the choice with useLocalStorage and respects prefers-color-scheme initially.
  2. Build an AuthContext (user, login, logout) and a <RequireAuth> wrapper component.
  3. Build a toast notification system: useToast().show("Saved") from anywhere; toasts auto-dismiss.
  4. Rebuild the cart with Zustand and compare the code.
  5. Show unnecessary re-renders in the Profiler, then fix them by splitting contexts.

Checkpoint

Why is context not a general state manager?Any change to the value re-renders all consumers and there are no selectors. Fine for rarely-changing values, wasteful for rapidly changing state.
Where should server data live?In a server-state cache (TanStack Query etc.), not copied into useState/Redux.
