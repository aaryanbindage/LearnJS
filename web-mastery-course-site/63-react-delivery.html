Lesson 63 — Testing pyramid, E2E & quality gates

Tests are how you change code without fear. A good test strategy catches the bugs that matter at the lowest cost, and automation (quality gates) keeps the standard without relying on willpower.

The testing trophy

LayerToolsWhat it provesCost / speed
StaticTypeScript, ESLint, PrettierTypos, wrong types, bad patterns, unreachable codecheapest, instant
UnitVitestPure logic: reducers, utilities, validators, algorithmscheap, milliseconds
Integration / componentVitest + Testing Library, MSW, TestcontainersComponents with their hooks and network; API handlers with a real DBmoderate; best return
End-to-endPlaywrightCritical user journeys in a real browser against a real stackexpensive, slow, flaky if careless
Visual / a11y / perfPlaywright screenshots, axe, Lighthouse CINo unintended UI/accessibility/performance regressionsmoderate

Guidelines: write tests that resemble how the software is used; the more your tests mirror real usage, the more confidence they give. Test behavior, not implementation: renaming a private function shouldn't break tests.

Mock Service Worker intercepts requests at the network layer, so your component's real fetch/TanStack Query code runs unchanged.

End-to-end with Playwright

Making E2E reliable

  • Use role/label locators, never CSS chains. Never sleep(); rely on auto-waiting and web-first assertions.
  • Isolate state: seed the database per test or per worker; log in once and reuse storageState; stub third-party services.
  • Keep E2E for critical journeys (signup, purchase, permissions); cover edge cases lower in the pyramid.
  • Capture traces/videos on failure (trace: "on-first-retry") and attach them to CI artifacts.
  • Quarantine flaky tests immediately and fix them; a test suite people ignore is worse than none.

Testing 3D and canvas

  • Extract logic (math, state, game rules) into pure functions and unit-test them; keep the render layer thin.
  • For R3F use @react-three/test-renderer to inspect the scene graph without a GPU.
  • Smoke-test in Playwright: page loads, no console errors, canvas present, a click triggers expected UI/HTML state; use screenshot comparisons with tolerance (GPU variation).
  • Track FPS/draw calls in a performance test using renderer.info exposed on window in test mode.

Quality gates in CI

  • Pre-commit hooks (husky + lint-staged) run fast checks on changed files; CI is the real gate.
  • Branch protection: require CI passing, reviews and up-to-date branches before merge.
  • Coverage is a smoke detector, not a goal: a high percentage with weak assertions proves nothing. Watch for untested critical paths, and use mutation testing (Stryker) occasionally to judge test quality.
  • Add bundle-size budgets (size-limit), Lighthouse CI thresholds, axe checks, dependency audit and secret scanning.
  • Test-driven development for tricky logic: write the failing test, make it pass, refactor.

Exercises

  1. Add MSW to Project 3 and write component tests for loading, success, empty and error states of one list page.
  2. Write 3 Playwright journeys (happy path, validation failure, permission denied) using role locators and a seeded test user; enable trace on retry.
  3. Create a GitHub Actions workflow running lint, typecheck, unit tests, build and E2E; require it for merging into main.
  4. Add axe checks to every Storybook story or Playwright page, and fail on serious violations.
  5. Write a test for a Three.js game-logic module (e.g., collision or scoring) with no rendering, then a Playwright smoke test for the canvas page.
  6. Introduce a bug on purpose and note which test layer catches it first. Then write the missing test that would have caught it earlier.

Checkpoint

Why query by role in Testing Library?It mirrors how users and assistive tech perceive the UI, so tests verify accessibility and survive markup refactors.
Why keep E2E tests few?They are slow, costly and more brittle. Cover only critical journeys end-to-end and push everything else down to faster layers.
