Lesson 68 — The 3D asset pipeline & optimization

Real 3D projects live or die on assets: how models are made, exported, compressed, loaded and budgeted. A 40 MB model that renders at 15 fps on a phone is a failed project, no matter how good the code is.

The pipeline

  1. Author in Blender (free) or another DCC tool: model, UV unwrap, texture (Substance Painter, Blender baking), rig and animate.
  2. Export as glTF 2.0 (.glb binary), "the JPEG of 3D". Apply transforms, use PBR materials (base color, metallic-roughness, normal, occlusion, emissive).
  3. Optimize: reduce polygons, merge meshes/materials, compress geometry and textures, prune unused data.
  4. Inspect in a glTF viewer (gltf.report, Don McCurdy's viewer, Blender re-import) and verify size, materials and animations.
  5. Load in Three.js/R3F with the right decoders, lazy-load, cache and dispose.

Blender export checklist

  • Units and scale: 1 unit = 1 meter; apply scale/rotation (Ctrl+A) before export so objects aren't oddly transformed.
  • One material per distinct look; fewer materials = fewer draw calls. Name everything meaningfully (you'll target nodes by name in code).
  • Delete hidden/unused geometry; keep tris reasonable; normals facing outward (turn on Face Orientation overlay).
  • Bake lighting and ambient occlusion into textures for static scenes; use lightmaps for large environments.
  • Export glTF Binary (.glb), "+Y Up", include only what you need (skip cameras/lights unless used), and enable "Compression" only if you'll serve the decoder; otherwise compress afterwards with gltf-transform.

Texture GPU memory is width × height × 4 bytes × 1.33 (mipmaps), regardless of JPEG/PNG file size. A single 4096² texture is ≈ 90 MB uncompressed. Use GPU-compressed formats (KTX2/Basis) to cut that 4–8×.

Measuring

  • Stats panels (stats.js, drei Stats, r3f-perf) show FPS/frame ms; renderer.info shows calls, triangles and GPU memory counts.
  • Chrome DevTools Performance with the GPU track; Spector.js to inspect individual draw calls; test on a real mid-range phone, not just your laptop.
  • Know whether you're CPU-bound (JS/draw-call overhead: frame time drops when you hide objects) or GPU-bound (frame time scales with resolution: lower DPR and see). Optimize the actual bottleneck.

Licensing and sourcing assets

  • Check licenses: CC0 (free for anything), CC-BY (credit required), no-derivatives and non-commercial restrictions exist. Keep an ASSETS.md with sources and licenses.
  • Sources: Poly Haven (CC0 models, HDRIs, textures), Sketchfab (varied licenses), Quaternius, Kenney (CC0 game assets), ambientCG, Mixamo (rigs and animations).

Exercises

  1. Download a 20+ MB glTF, run gltf-transform inspect, then optimize it (Draco/Meshopt + KTX2 + resize). Report size, load time and visual differences before and after.
  2. Model a simple prop in Blender (UV unwrapped, PBR textured), export .glb, and load it with decoders configured in Three.js.
  3. Build a scene with 200 separate meshes of 50 materials, then reduce it to < 30 draw calls by merging, atlasing and instancing. Record renderer.info before and after.
  4. Add LOD to a forest of 2,000 trees (3 levels incl. billboard) and show triangle count drop at distance.
  5. Write a disposeObject and a test scene that adds/removes models 100 times; prove with renderer.info.memory that nothing leaks.
  6. Profile the same scene on a phone via remote debugging; identify CPU vs GPU bound and fix the top bottleneck.

Checkpoint

Why doesn't a smaller JPEG reduce GPU memory?The GPU stores textures decompressed (width × height × 4 bytes plus mipmaps). Only GPU-compressed formats like KTX2/Basis stay compressed in VRAM.
How do you tell CPU-bound from GPU-bound?Lower the canvas resolution: if FPS improves a lot, you're GPU/fill-rate bound. If not, reduce draw calls or JS work: if that helps, you're CPU-bound.
