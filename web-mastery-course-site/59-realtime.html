Lesson 59 — Real-time: WebSockets & multiplayer state

Chat, live cursors, collaborative editing, multiplayer 3D worlds. HTTP is request/response; real-time apps need the server to push. Learn the transports and, more importantly, how to keep distributed state consistent.

Choosing a transport

OptionDirectionUse when
Pollingclient pulls repeatedlySimple, low frequency updates (every 10–60 s); easy to scale
Server-Sent Events (SSE)server → client, over plain HTTPLive feeds, notifications, streaming LLM tokens; auto-reconnect built in
WebSocketfull duplex, persistentChat, games, collaboration, anything needing low-latency two-way messages

Managed options when you don't want to run socket servers: Pusher, Ably, Supabase Realtime, Firebase, PartyKit/Cloudflare Durable Objects, Liveblocks, Socket.IO (library with fallbacks and rooms).

SSE in 20 lines

WebSockets: a chat room

  • Authenticate the connection (cookie on upgrade or a short-lived ticket in the first message). Authorize each message; check Origin to prevent cross-site WebSocket hijacking.
  • Scaling: sockets are stateful. With multiple servers, broadcast through a pub/sub backplane (Redis Pub/Sub, NATS) and use sticky sessions or a shard-by-room design.
  • Backpressure: slow clients must not exhaust memory; drop or coalesce updates when bufferedAmount grows.

Multiplayer state: the hard part

Networks have latency, jitter, loss and reordering. Two players acting at the same time must end up with the same world. Common models:

ModelHowSuitable for
Authoritative serverClients send inputs; server simulates and broadcasts state. Clients render it.Games, anti-cheat, anything where the server owns truth
Client prediction + reconciliationClient applies its own input immediately; when authoritative state arrives, rewind and replay unacknowledged inputsResponsive character movement
InterpolationRender remote entities ~100 ms in the past, blending between received snapshotsSmooth other players
Last-writer-winsLatest timestamp overwritesSimple fields (cursor position, a status)
Operational Transform / CRDTsMerge concurrent edits deterministically (Yjs, Automerge, Loro)Collaborative documents, whiteboards, offline-first sync

Multiplayer 3D (Three.js / R3F) in practice

  • Send inputs and small state deltas, not whole scenes. Quantize numbers (positions to 2 decimals or int16), use binary formats (MessagePack, Protobuf, FlatBuffers) as you scale.
  • Tick the simulation at a fixed rate (20–60 Hz) separate from render FPS; render with interpolation.
  • Use rooms to limit who receives what (area-of-interest filtering).
  • Frameworks: Colyseus (authoritative rooms), PartyKit, Liveblocks, Socket.IO, Yjs with y-websocket for shared documents and presence (live cursors).

Exercises

  1. Build a chat room with the ws server above: usernames, history of the last 50 messages, typing indicators, and reconnection with backoff.
  2. Add authentication to the socket (session cookie) and per-user rate limiting (messages/second); test with a malicious client script.
  3. Stream a fake LLM response token by token with SSE and render it progressively in React.
  4. Add live cursors to your Project 3 app using PartyKit or Liveblocks presence.
  5. Build a 3D "lobby": each connected player is a cube in a shared Three.js scene; send input at 20 Hz; interpolate remote players; add client-side prediction for your own cube.
  6. Make a collaborative to-do list with Yjs and verify it merges offline edits from two tabs.

Checkpoint

SSE vs WebSocket?SSE is one-way server→client over HTTP with built-in reconnection, ideal for feeds and streaming. WebSocket is a full-duplex persistent channel for two-way, low-latency messaging.
Why interpolate remote players?Updates arrive discretely and late. Rendering slightly in the past and blending between snapshots hides jitter and gives smooth motion.
