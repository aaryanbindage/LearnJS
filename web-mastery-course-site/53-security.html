Lesson 53 — Web security: XSS, CSRF, CSP & auth

Every app you ship will be probed by automated attackers within hours. Security is a set of habits, not a feature you add at the end. This lesson is defensive: understand each attack so you can prevent it in your own code.

Threat model basics

  • Never trust client input. Anything from the browser (forms, headers, cookies, URL, localStorage, even your own frontend's checks) can be forged. Validate and authorize on the server.
  • Least privilege, defense in depth (multiple layers), secure by default, fail closed.
  • Use the OWASP Top 10 as a checklist: broken access control, cryptographic failures, injection, insecure design, misconfiguration, vulnerable components, authentication failures, integrity failures, logging failures, SSRF.

XSS: Cross-Site Scripting

If attacker-controlled text is interpreted as HTML/JS in your page, their script runs with your user's session: it can read data, make requests as the user and steal tokens. Types: stored (saved in DB), reflected (from URL), DOM-based (client JS writes unsafe HTML).

Defenses

  1. Output-encode by default. React, Vue and other frameworks escape interpolated text. Danger zones: dangerouslySetInnerHTML, innerHTML, insertAdjacentHTML, document.write, eval, new Function, javascript: URLs in href, and unvalidated href/src.
  2. Sanitize HTML you must render (rich text, markdown) with DOMPurify (or the Sanitizer API when available). Sanitize on output, with an allow-list.
  3. Content Security Policy (CSP): a response header restricting where scripts can come from. Even if an injection slips through, inline/unknown scripts won't run.
  4. Cookies with HttpOnly so JS can't read session tokens.
  5. Trusted Types (Chromium): forbid raw strings reaching dangerous sinks.

CSRF: Cross-Site Request Forgery

A malicious site makes the victim's browser send a request to your site; the browser attaches the victim's cookies automatically, so the request looks authenticated (POST /transfer?to=attacker).

Defenses

  • SameSite=Lax or Strict cookies (Lax is the modern browser default): cookies aren't sent on cross-site POSTs.
  • CSRF tokens (synchronizer or double-submit) for state-changing requests when using cookie auth, or require a custom header (X-Requested-With) / JSON content type with strict CORS.
  • Never change state on GET. Check Origin/Referer headers.

Authentication & passwords

  • Never store plaintext passwords. Hash with a slow, salted algorithm: argon2id (preferred), scrypt or bcrypt. Never roll your own crypto; never use fast hashes (SHA-256, MD5) for passwords.
  • Prefer a proven auth provider/library (Auth.js, Clerk, Supabase Auth, Auth0, Lucia patterns, Passkeys/WebAuthn) over building from scratch.
  • Passkeys (WebAuthn) are phishing-resistant and the best UX. Offer MFA (TOTP/WebAuthn).
  • Sessions vs JWT: server sessions with an HttpOnly cookie are simplest and revocable. JWTs are fine for short-lived API tokens but hard to revoke; don't store them in localStorage for sensitive apps.
  • Rate-limit login, add lockout/backoff, generic error messages ("invalid credentials"), secure password reset (single-use, expiring tokens).
  • Authorization is separate from authentication: check permissions on every request, for every resource (broken object-level authorization: GET /orders/1234 must verify that order belongs to the user).

Transport, headers, CORS and secrets

  • HTTPS everywhere; HSTS (Strict-Transport-Security). No mixed content.
  • Helpful headers: X-Content-Type-Options: nosniff, Referrer-Policy: strict-origin-when-cross-origin, Permissions-Policy, COOP/COEP when you need cross-origin isolation. In Express use helmet.
  • CORS is not a security boundary for your server; it only tells browsers which origins may read responses. Don't use Access-Control-Allow-Origin: * with credentials. Allow-list origins.
  • Secrets: never in source control or frontend bundles (anything in VITE_*/NEXT_PUBLIC_* is public). Use environment variables / secret managers, rotate leaked keys immediately, add .env to .gitignore, scan with gitleaks.

Supply chain security

  • Most of your code is dependencies. Keep them few and maintained; commit the lockfile; run npm audit, Dependabot/Renovate, and npm ci in CI.
  • Beware typosquatting and malicious postinstall scripts; check download counts, repo, maintainers. Consider --ignore-scripts in CI and provenance/SBOM tooling.
  • Subresource Integrity for third-party scripts: <script src integrity="sha384-…" crossorigin>. Minimize third-party tags (analytics, chat widgets run with full page power).

Privacy and compliance (briefly)

  • Collect the minimum data; define retention; encrypt in transit and at rest; log without secrets or PII.
  • Know the regulations relevant to your users (GDPR, CCPA) and basic obligations: consent, deletion/export, breach notification.

Exercises

  1. Build a comment box that is deliberately XSS-vulnerable, exploit it with a harmless payload in a local sandbox, then fix it three ways (escape, DOMPurify, CSP) and verify each.
  2. Write a Node endpoint with a SQL injection hole, demonstrate it on a local SQLite file, then fix it with parameters.
  3. Add a strict CSP (report-only first) to a Vite/Next app and fix everything that breaks.
  4. Implement cookie-based login with an HttpOnly; Secure; SameSite=Lax session, CSRF token protection, and rate limiting.
  5. Write tests proving user A cannot read or edit user B's resource (object-level authorization).
  6. Run npm audit, gitleaks and a ZAP baseline scan against your local project; triage the findings.
  7. Work through the free PortSwigger Web Security Academy labs for XSS, CSRF and SQLi.

Checkpoint

Why is client-side validation not security?Attackers bypass your frontend and send requests directly. Client validation helps users; only server-side checks protect the system.
How does HttpOnly help against XSS?JavaScript can't read HttpOnly cookies, so an injected script can't steal the session token (it can still make requests as the user, so you must also prevent XSS).
