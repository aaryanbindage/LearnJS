Lesson 30 — React performance, patterns & testing

Make apps fast, structure complex components cleanly, and test them like a user would.

How React renders (the mental model)

  1. Trigger: state change (or initial mount).
  2. Render: React calls your component functions to compute the new tree (must be pure).
  3. Commit: React applies the differences to the DOM; then runs effects.

A parent re-render re-renders its children by default. Rendering ≠ DOM updating: React only touches the DOM for real differences. Most performance problems are from too much work per render or too many renders.

Measure first

  • React DevTools Profiler: record an interaction, see which components rendered and why (enable "Record why each component rendered").
  • Chrome Performance panel and Lighthouse for load and runtime.
  • Test with production builds and CPU throttling: dev mode is slower.

Fixes in order of preference

  1. Move state down: state that only one subtree uses should live there, so it doesn't re-render the whole app.
  2. Lift content up / use children: a slow subtree passed as children isn't re-created when the wrapper's state changes.
  3. Avoid expensive work in render: useMemo for heavy computations.
  4. memo + stable props for large, frequently re-rendered children.
  5. Virtualize long lists (render only visible rows): @tanstack/react-virtual, react-window.
  6. Transitions: useTransition marks an update as non-urgent so typing stays responsive.
  7. Code-split routes and heavy libraries (lazy/import()); analyze with rollup-plugin-visualizer.
  8. Optimize assets: image sizes/formats, fonts, loading="lazy".

Patterns worth knowing

Also: portals (createPortal for modals/tooltips), error boundaries, forwardRef (React 19: ref is a normal prop), headless UI libraries (Radix, React Aria) for accessible primitives.

Testing React

Test what users see and do, not implementation details. Vitest + React Testing Library + user-event is the standard stack.

  • Query priority: getByRole → getByLabelText → getByText → getByTestId (last resort).
  • Use findBy* for async appearance; queryBy* to assert absence.
  • End-to-end: Playwright drives a real browser through full user flows.

Exercises

  1. Profile an app you built; find the most expensive re-render and fix it with state colocation before reaching for memo.
  2. Render a 10,000-row table; make it fast using virtualization.
  3. Build a compound Accordion with keyboard support and ARIA.
  4. Write tests for your todo app: add, toggle, delete, empty state, and filter.
  5. Write one Playwright test covering the full "login → add to cart → checkout" flow.
  6. Reduce your app's initial JS bundle by 30% with route-level code splitting; show before/after.

Why query by role in tests?It mirrors how users and assistive tech find elements, so tests double as accessibility checks and survive refactors of markup.
