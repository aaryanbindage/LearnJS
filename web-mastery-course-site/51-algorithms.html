Algorithms hiding in web work

  • Virtual DOM diffing (React reconciliation): tree diff with keys → heuristics for O(n).
  • Debounce/throttle, rate limiting (token bucket), LRU cache, memoization.
  • Fuzzy search (edit distance, trigram, Fuse.js), autocomplete (trie), sorting/filtering large tables (virtualization + indexes).
  • Layout engines (flexbox), spatial indexes (quadtree, BVH) for collision and raycasting, pathfinding (A*) in games, geometry (dot/cross products, projections, lerp, quaternions) in 3D.
  • Cryptographic hashing, compression, CRDTs for collaborative editing.

A method for solving problems

  1. Restate the problem; list inputs, outputs, constraints and edge cases (empty, one item, duplicates, huge).
  2. Do a tiny example by hand.
  3. Write the brute-force solution first and state its complexity.
  4. Find the bottleneck; pick a structure/pattern (hash map, sort + two pointers, BFS, DP) to remove it.
  5. Code it, then test with edge cases. State the final time and space complexity.

Exercises

  1. Implement a MinHeap and use it for "top 10 of 1,000,000 numbers" in O(n log k).
  2. Implement a Trie with insert and suggest(prefix); wire it to a live autocomplete input.
  3. Implement an LRU cache with O(1) get/set (Map or doubly-linked list + Map).
  4. Flatten and unflatten a nested comments tree from a flat list with parentId in O(n).
  5. Implement A* on a 2D grid and visualize it on canvas (Lesson 46).
  6. Solve 20 problems from NeetCode/LeetCode "easy–medium" across arrays, hashing, two pointers, trees, graphs and DP; write down the pattern used for each.

Checkpoint

Why convert an array to a Set before many lookups?Array includes is O(n) per lookup; Set.has is O(1) on average, turning an O(n·m) algorithm into O(n + m).
When is premature optimization not premature?When data sizes can grow large (lists of thousands, per-frame loops, large graphs) and a quadratic algorithm is on the hot path. Choosing the right structure is free; micro-tuning is not.
