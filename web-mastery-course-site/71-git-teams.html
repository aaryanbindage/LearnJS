Lesson 71 — Git, code review & team workflow

Writing code is half the job; the other half is changing a shared codebase safely with other people. Git fluency, small reviewable changes and good communication separate juniors from professionals.

Git mental model

  • A commit is an immutable snapshot with a parent pointer. A branch is a movable label pointing at a commit. HEAD is "where you are".
  • Three areas: working tree → (git add) → index/staging → (git commit) → repository. Remotes (origin) are other copies; fetch downloads, pull = fetch + merge/rebase, push uploads.
  • History is a graph (DAG). Most "scary" Git operations are just moving labels around it, and the reflog remembers almost everything for a while.

Fixing mistakes

Amend the last commit (not yet pushed)git commit --amend
Undo a pushed commit safelygit revert <sha> (creates a new commit)
Squash/reorder/edit local commits before reviewgit rebase -i origin/main (fixup, squash, reword)
Fixup a specific earlier commitgit commit --fixup <sha> then git rebase -i --autosquash origin/main
Lost commits after a bad reset/rebasegit reflog → git switch -c rescue <sha>
Find which commit introduced a buggit bisect start; git bisect bad; git bisect good <sha> (binary search; git bisect run npm test automates it)
Who changed this line and why?git blame -L 40,60 file, git log -S "symbol" -p
Merge conflictsEdit conflict markers, git add, git rebase --continue (or merge --continue). Enable git config rerere.enabled true
Bring one commit to another branchgit cherry-pick <sha>
Work on two branches at oncegit worktree add ../hotfix hotfix/123
Golden ruleDon't rewrite (rebase/amend/force-push) history other people have based work on: shared branches like main. Rewrite your own feature branch freely until it's reviewed.

Branching strategies

  • Trunk-based development (most high-performing teams): short-lived branches (< 1–2 days) merged to main often, hidden behind feature flags if incomplete. Pairs with strong CI and fast review.
  • GitHub Flow: branch → PR → review → merge → deploy. Simple and fine for most products.
  • Git Flow (long-lived develop/release branches): heavy; mostly for versioned, packaged software.
  • Merge styles: squash merge (one clean commit per PR; common), rebase merge (linear), merge commit (preserves branch topology). Pick one per repo.

Commits and pull requests that people can review

  • Small PRs (< ~300 changed lines) get reviewed faster and better. Split refactors from behavior changes. Stack PRs for big features.
  • Commit messages: imperative subject ≤ 72 chars; body explains why. Conventional Commits (feat:, fix:, chore:, docs:, refactor:) enable changelogs and automated versioning.
  • PR description: what/why, how to test, screenshots or video for UI, risks, rollout/rollback plan, linked issue.
  • Self-review the diff first. Run the checks locally. Mark WIP as draft.

Code review: giving and receiving

As a reviewer

  • Review for: correctness, edge cases, security, tests, readability, API design, performance on hot paths, accessibility. Don't nitpick what a linter/formatter should catch.
  • Ask questions rather than issue verdicts ("What happens if this list is empty?"). Prefix severity: blocking:, suggestion:, nit:, question:. Praise good work.
  • Respond quickly (same day). A slow review queue is the biggest hidden cost in teams.

As an author

  • Assume good intent; the review is about the code, not you. Reply to every comment, push fixes as new commits during review, and resolve threads when done.
  • If a discussion drags on, jump on a quick call and write the outcome in the PR.

Repository hygiene & automation

  • .gitignore (node_modules, build output, .env), a committed lockfile, .editorconfig, Prettier + ESLint, CODEOWNERS, branch protection (require review + passing CI, no direct pushes to main), signed commits optionally.
  • Hooks with husky/lint-staged for fast local checks; never rely on them alone (CI is the gate).
  • Secrets committed by accident are compromised forever: rotate the key immediately; then clean history (git filter-repo) as a secondary step.
  • Monorepos: sparse checkout and tools like Turborepo/Nx for affected-only builds. Releases: semantic versioning, tags, changelogs (Changesets, release-please).
  • Documentation: README (what, why, quick start), CONTRIBUTING, ADRs (short Architecture Decision Records: context, decision, consequences), runbooks.

Working with others

  • Write things down: issues with acceptance criteria, design docs for big changes (problem, options, decision, risks), async updates. Over-communicate status and blockers.
  • Estimate with ranges and slice work into vertical, shippable increments. Prefer reversible decisions; make irreversible ones deliberately.
  • Pair/mob when stuck or onboarding; rotate knowledge so no one is a single point of failure.
  • Open-source contribution is the best practice: read CONTRIBUTING, start with "good first issue", discuss before large changes, keep PRs small.

Exercises

  1. Create a repo; make a feature branch with 5 messy commits and use interactive rebase to turn them into 2 clean ones. Then deliberately cause and resolve a merge conflict, using rerere.
  2. Introduce a bug across 30 commits (script it) and find it with git bisect run.
  3. Destroy a branch with reset --hard then recover it from the reflog.
  4. Set up branch protection, CODEOWNERS, a PR template, conventional-commit linting (commitlint) and release-please on a practice repo.
  5. Find a "good first issue" in an open-source JS/Three.js project, read its contribution guide, and submit a real PR (docs fixes count).
  6. Review three PRs from others (or open-source) using the severity-prefix convention, and write an ADR for a decision in your Project 5.

Checkpoint

Merge vs rebase?Merge joins histories with a merge commit and preserves the true timeline. Rebase replays your commits on a new base for a linear history, but rewrites them, so use it only on unshared branches.
Why small PRs?They're easier to understand, review thoroughly, test and roll back, and they merge sooner, reducing conflicts.
