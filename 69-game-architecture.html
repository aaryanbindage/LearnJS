Lesson 69 — Game architecture: loops, ECS, physics & input

Interactive 3D is a real-time simulation. Games force you to solve timing, state, collisions and input properly, and these skills carry into any complex interactive app (editors, simulations, visualizations).

The game loop: fixed timestep

Rendering runs at whatever frame rate the display allows (30/60/120/144 Hz). If your simulation uses the raw frame delta, behavior varies with frame rate and physics becomes unstable. The standard fix: simulate at a fixed step (e.g., 1/60 s) using an accumulator, then render with interpolation.

Compare 15 fps and 144 fps with the box unchecked: the bounce behavior changes (energy gain/loss from integration error). With a fixed step it is consistent. Run it to see.

Entity Component System (ECS)

  • Entity: just an id. Component: plain data (Position, Velocity, Health, MeshRef). System: function that processes all entities having certain components (MovementSystem, CollisionSystem, RenderSyncSystem).
  • Favors composition over deep inheritance (Enemy extends Character extends GameObject… collapses when you need a flying, exploding, friendly enemy).
  • Data-oriented layout (arrays of components) is cache-friendly and easy to serialize, replay and sync over a network.

  • Rigid bodies: dynamic (simulated), fixed (static world), kinematic (you move it, it pushes others). Colliders: use primitive shapes (box, sphere, capsule) or convex hulls; avoid per-triangle trimesh colliders for dynamic objects.
  • Collision events and sensors (trigger zones) drive game logic: pickups, damage, doors.
  • Keep the physics world as the source of truth for positions of simulated bodies, and copy transforms to meshes each frame. Don't move both.
  • Character controllers: use the engine's kinematic controller (handles slopes, steps, sliding) instead of a dynamic box with forces.
  • Tunneling (fast objects passing through thin walls): use continuous collision detection (CCD), smaller steps or thicker colliders.

Input handling

  • Track input state (which keys are down) via keydown/keyup into a map, then read it inside the loop. Use event.code (KeyW) for layout-independent controls.
  • Pointer events unify mouse, touch and pen. Use setPointerCapture for drags. Pointer Lock API for FPS mouse-look.
  • Gamepad API (navigator.getGamepads()) is polled each frame. On mobile, provide on-screen joysticks and design for thumbs.
  • Add an input abstraction (actions like "jump", "move") so keyboard, gamepad and touch map to the same game logic and remapping is easy.
  • Always respect accessibility: remappable keys, avoid flashing, reduced motion, pause on blur (visibilitychange).

Game state, scenes and structure

  • State machines for game flow (menu → loading → playing → paused → game over) and for entity AI (idle, patrol, chase, attack).
  • Event bus for decoupled communication (enemyKilled → score, sound, particles).
  • Save/load: serialize plain data (ECS makes this easy); version your save format; use IndexedDB/localStorage.
  • Audio (Lesson 70), asset loading screens, settings (quality presets), object pooling for bullets/particles to avoid GC pauses, debug tools (stats, physics debug view, god mode, time scale).
  • Determinism: seeded random + fixed timestep + input recording gives replays and easier netcode/testing.

Checkpoint

Why a fixed timestep for physics?Physics integration is only stable and reproducible with a constant dt. Variable frame deltas cause frame-rate dependent behavior, jitter and tunneling.
What does ECS give you over inheritance?Behavior is built by combining data components and systems, so new entity types don't need new class hierarchies; data is easier to serialize, test and process efficiently.
