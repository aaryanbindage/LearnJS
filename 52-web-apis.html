Lesson 52 — Workers, service workers, IndexedDB & PWAs

The browser is a full application platform. These APIs let you do heavy work off the main thread, work offline, store large data, and install your app like a native one.

Web Workers: parallelism

JavaScript runs on one main thread, so a heavy loop freezes the UI. A Worker is a separate thread with its own global scope (no DOM) that communicates by message passing (structured clone). Use it for parsing, compression, image processing, physics, search indexing, WASM.

Other worker kinds: Shared Workers (shared across tabs), Service Workers (network proxy, below), Worklets (audio, paint).

Service workers: offline and caching

A service worker is a script that sits between your page and the network. It can intercept fetch requests, serve from cache, enable offline use, background sync and push notifications. It requires HTTPS (localhost is allowed) and has a lifecycle: register → install → activate → fetch.

  • Strategies: cache-first (static assets), network-first (HTML, fresh data), stale-while-revalidate (good default for assets/APIs), network-only (auth, payments).
  • Stale caches are the main bug source. Version caches, delete old ones, and give users an "update available" prompt.
  • Use Workbox (or vite-plugin-pwa) rather than hand-writing production service workers.

Installable PWA

Link it with <link rel="manifest" href="/manifest.webmanifest"> and add <meta name="theme-color">. With a service worker and manifest, browsers offer an "install" option. Check with Lighthouse and DevTools → Application.

IndexedDB: a real client-side database

localStorage is synchronous, string-only and ~5 MB. IndexedDB is asynchronous, transactional, stores structured data (including Blobs and typed arrays) and handles hundreds of MB. Its raw API is clunky, so use a wrapper like idb or Dexie. (It's not available in the sandboxed demos here, so run these in your own project.)

Storage: navigator.storage.estimate() shows quota; navigator.storage.persist() asks the browser not to evict your data. Offline-first apps sync a local DB with a server and resolve conflicts (see CRDTs, RxDB, PowerSync, Replicache).

Exercises

  1. Move a heavy computation (image blur, big JSON parse, fuzzy search index) to a Worker; compare INP before and after. Add Comlink.
  2. Render a Three.js scene with OffscreenCanvas in a Worker; keep UI and canvas smooth during main-thread load.
  3. Make your Project 2 todo app a PWA: manifest, service worker (stale-while-revalidate), offline page, install prompt, and "new version available" toast. Verify with Lighthouse.
  4. Replace localStorage with IndexedDB (Dexie) for notes with tags and full-text-ish search; handle quota errors.
  5. Add background sync: queue failed POSTs while offline and replay them when connectivity returns.
  6. Use BroadcastChannel to keep two open tabs of your app in sync.

Checkpoint

Why can't a worker touch the DOM?The DOM isn't thread-safe. Workers have their own scope and communicate through messages; the main thread applies UI updates.
What's the riskiest part of service workers?Stale caches: users stuck on old code. Version your caches, clean up on activate, and plan an update flow.
