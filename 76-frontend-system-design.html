Lesson 76 — Front-end system design

System design is deciding how the pieces of a product fit together under real constraints: users, scale, devices, teams, deadlines. It's the skill that turns "I can build components" into "I can own a product", and it's the core of senior interviews.

A framework for any design question

  1. Clarify requirements: users, core features, what's out of scope. Functional (what it does) and non-functional (latency, offline, accessibility, devices, i18n, SEO, security, scale).
  2. Define the data and API: entities, relationships, endpoints/events, pagination, errors, real-time needs.
  3. Sketch the architecture: components/modules, rendering strategy, state ownership, data flow, caching layers.
  4. Go deep on the hard parts: performance, consistency, failure modes, accessibility, security.
  5. Discuss trade-offs and evolution: alternatives considered, what you'd measure, how it grows. There is no perfect design, only justified ones.

Worked example 1: a news-feed / social timeline

  • Requirements: infinite scroll, posts with images/video, like/comment optimistic, new-post indicator, works on slow mobile, accessible, SEO for public posts.
  • Data/API: GET /feed?cursor=…&limit=20 returns posts + next cursor; normalized store of posts/users by id; POST /posts/:id/like idempotent.
  • Rendering: SSR the first page (fast LCP + SEO), hydrate; subsequent pages client-fetched. Stream the shell; Suspense per module.
  • Performance: virtualize the list (windowing: only visible rows in DOM), reserve image dimensions (no CLS), lazy-load media with IntersectionObserver/loading="lazy", responsive images (AVIF), video poster + load on demand, prefetch next page near the end, request cancellation.
  • State: TanStack Query infinite query keyed by feed type; optimistic like with rollback; deduplicate posts across feeds via normalized cache.
  • Freshness: poll or SSE "new posts available" pill (don't shift content under the user's cursor), update on focus.
  • A11y: role="feed" with article items, focus management on load more, announce new content politely, keyboard shortcuts documented, reduced motion.
  • Failure modes: partial failures (one media fails), retry/backoff, offline banner, empty/error states, duplicate/out-of-order responses (use request ids or keys).

Worked example 2: autocomplete / typeahead

  • Flow: input → debounce (150–300 ms) → request → results; cancel in-flight requests (AbortController) so stale responses never overwrite newer ones.
  • Caching: cache by normalized query (prefix reuse), in memory + HTTP cache; prefetch popular queries; local filtering when the dataset is small (trie / fuzzy search in a Worker).
  • Ranking on the server (popularity, recency, personalization); highlight matches; keep latency < 100 ms perceived.
  • A11y (ARIA combobox pattern): role="combobox", aria-expanded, aria-controls, aria-activedescendant, arrow keys / Enter / Escape, announce result count in a live region. Better: use a headless library (“Design systems & component libraries”).
  • Edge cases: IME composition, paste, very fast typing, empty results, errors, mobile keyboards.

Worked example 3: a collaborative 3D editor (Figma-for-3D)

  • Architecture: an engine layer (scene graph, commands, undo stack, picking, gizmos, in Three.js, framework-agnostic) separated from a React shell (panels, inspector, toolbars) that subscribes to engine state.
  • State: scene document as serializable data (the source of truth) → rendered into Three objects. Command pattern for every edit → undo/redo, autosave, and sync via operations.
  • Collaboration: CRDT (Yjs) or operational log over WebSocket; presence cursors and selections; conflict handling per property; authoritative server for permissions.
  • Performance: render on demand (not continuous), instancing, BVH picking, LOD, Web Workers/OffscreenCanvas for heavy import/processing, progressive loading of assets, GPU memory budget and eviction.
  • Persistence/offline: IndexedDB autosave, versioned document schema with migrations, asset storage in object storage with content hashing.
  • Quality: golden-image tests for rendering, property-based tests for commands (apply + undo = identity), perf budgets in CI.

Communicating a design

  • Draw boxes and arrows: client components, stores, network, server/cache/DB, with data flow labeled. Write the API shapes.
  • State assumptions out loud, quantify (requests/s, payload sizes, list lengths, latency budget), and name the trade-off of each decision ("optimistic updates feel instant but need reconciliation").
  • Write a short design doc / RFC for real work: context, goals/non-goals, proposal, alternatives, risks, rollout, open questions. Get feedback before building.

Exercises

  1. Do a 45-minute written design for each: news feed, autocomplete, chat app, photo gallery, kanban board, video player, collaborative whiteboard, e-commerce product page. Use the 5-step framework and the checklist.
  2. Implement the virtualized list with variable row heights and keyboard navigation; compare memory and scroll FPS with the naive list at 100k rows.
  3. Build the autocomplete with cancellation, caching and full combobox ARIA; test with a screen reader.
  4. Write an RFC for a real change in Project 5 (e.g., adding offline support) with alternatives and a rollout plan; have a peer review it.
  5. Study two public engineering write-ups (e.g., how a large company built their feed or editor) and summarize the decisions and trade-offs in one page.
  6. Run a mock system design interview with a peer (30 min each way) and give each other feedback on structure, depth and communication.

Checkpoint

Why cancel in-flight requests in autocomplete?Responses can arrive out of order. Without cancelation (or ignoring stale responses), an older slower response may overwrite the newer query's results.
What does virtualization trade off?Huge performance and memory gains in exchange for complexity: measurement of variable heights, scroll restoration, find-in-page, and accessibility semantics need extra care.
