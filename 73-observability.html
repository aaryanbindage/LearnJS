Lesson 73 — Observability, monitoring & incident response

Production will surprise you. Observability is your ability to ask "what is the system doing and why?" from the outside, without shipping new code. It turns outages from mysteries into short, calm investigations.

The three pillars (plus one)

Structured logging

  • Generate a request/correlation id at the edge, include it in every log line and response header (X-Request-Id), and propagate it to downstream calls.

Metrics that matter: RED and USE

  • RED for request-driven services: Rate (req/s), Errors (% failing), Duration (latency: p50/p95/p99, never just the average).
  • USE for resources: Utilization, Saturation (queues, waits), Errors (CPU, memory, DB connections, disk).
  • Four golden signals (Google SRE): latency, traffic, errors, saturation.
  • Business metrics too: signups, checkouts, jobs completed. Often the first sign something's wrong.

SLOs, alerts and on-call

  • SLI (a measurement, e.g., % of requests under 300 ms) → SLO (a target, 99.5% over 30 days) → error budget (the allowed 0.5%). When the budget is spent, prioritize reliability over features.
  • Alert on symptoms users feel (error rate, latency, failed checkouts), not on every cause (CPU 80%). Every alert must be actionable, link to a runbook and page a human only when needed. Alert fatigue hides real incidents.
  • Uptime/synthetic checks from outside (Better Stack, Checkly, UptimeRobot, Playwright against prod) and a public status page.
  • Know your dashboards before the incident: one overview (RED), one per service, one for dependencies (DB, queue, third parties).

Incident response

  1. Detect and declare: name an incident commander; open a channel/doc with a timeline.
  2. Mitigate first, diagnose second: roll back, disable the feature flag, scale up, fail over. Restore service before finding the root cause.
  3. Communicate: status page updates every ~30 min, plain language, no speculation.
  4. Diagnose: what changed recently (deploy, config, traffic, dependency)? Follow traces/logs by request id. Form hypotheses and test them one at a time.
  5. Resolve and verify using metrics, then monitor.
  6. Blameless postmortem: timeline, impact, root causes (systems, not people), what went well, and tracked action items with owners. Share it widely.
Debugging in productionReproduce with the request id; read the trace; check recent deploys; compare healthy vs unhealthy instances; use feature-flagged verbose logging; never attach a debugger to prod or log secrets while investigating.

Exercises

  1. Add pino with request ids and redaction to your API; confirm secrets never appear in logs. Query the logs by request id.
  2. Expose Prometheus metrics, run Prometheus + Grafana via docker compose, and build a RED dashboard. Generate load with k6 or autocannon and watch p95 move.
  3. Instrument with OpenTelemetry, send traces to Jaeger/Tempo (docker), add an artificial slow query, and find it in a trace.
  4. Integrate Sentry in the front end with source maps and release tagging. Throw a deliberate error and trace it to the exact line and commit.
  5. Define two SLOs for Project 5 and create alerts with runbook links; simulate a failure and verify the alert fires.
  6. Run a game-day: break something on purpose in staging, practice the incident steps, and write a blameless postmortem.

Checkpoint

Why percentiles instead of average latency?Averages hide the slow tail. If 1% of requests take 10 s, the average looks fine while real users suffer. p95/p99 expose that.
Mitigate vs fix?Mitigation (rollback, flag off) stops the harm quickly; the root-cause fix can wait until service is restored and you can investigate calmly.
