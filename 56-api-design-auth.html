Lesson 56 — API design, validation & authentication

An API is a product whose users are other programmers (including you in six months). Good APIs are consistent, predictable, hard to misuse and safe.

REST principles in practice

  • Resources are nouns, methods are verbs: GET /api/orders/42, POST /api/orders, DELETE /api/orders/42. Plural collection names.
  • Nest sparingly: /users/7/orders is fine; deeper than two levels becomes awkward. Expose actions that don't fit CRUD as sub-resources: POST /orders/42/cancel.
  • Stateless: each request carries what the server needs (token). No server-side session assumptions in handlers beyond auth.
  • Status codes and bodies: use the right code; JSON everywhere; consistent envelope or none (pick one).
  • Versioning: /v1/… or a header. Prefer additive, backwards-compatible changes (new optional fields) so you rarely need a new version.
  • Idempotency: retries must be safe. Accept an Idempotency-Key header for POSTs that charge money or create things.
  • Return money as integer minor units (cents) plus currency; dates as ISO-8601 UTC strings; ids as opaque strings.
  • Expose the minimum fields (never return password hashes); version your DTOs separately from DB rows.
  • Document with OpenAPI (Swagger UI, Scalar). Generate types/clients from it, or the reverse from Zod schemas (zod-to-openapi).

Validation: the boundary rule

Parse, don't validate: turn unknown input into a trusted typed value at the edge, then pass only trusted data inward. Validate bodies, query strings, params and headers.

Authentication: who are you?

Passwords done right

Server sessions (recommended default for web apps)

Tokens (JWT), OAuth/OIDC and passkeys

  • JWT: a signed (not encrypted!) JSON blob: header.payload.signature. Stateless, but you can't revoke it before expiry. Use short lifetimes (5–15 min) plus a refresh token, always verify alg, exp, iss, aud, and never put secrets in the payload.
  • OAuth 2.0 / OpenID Connect: "Sign in with Google/GitHub". Use the Authorization Code flow with PKCE; let a library (Auth.js, Better Auth, Lucia patterns, Clerk, Auth0, Supabase) handle it.
  • Passkeys / WebAuthn: public-key credentials stored in the device/password manager. Phishing-resistant and the best UX; use @simplewebauthn.
  • MFA: TOTP apps or WebAuthn; avoid SMS where possible.

Authorization: what may you do?

Protecting your API

  • Rate limiting (per IP and per account): token bucket in Redis; stricter on login, signup, password reset. Return 429 with Retry-After.
  • Limits: body size, pagination size, query depth/complexity (GraphQL), upload types and sizes, request timeouts.
  • CORS allow-list; CSRF protection when using cookies (“Web security: XSS, CSRF, CSP, auth”); security headers (helmet).
  • Webhooks: verify signatures (HMAC) and timestamps; make handlers idempotent.
  • Audit logs for sensitive actions; alert on anomalies.

Exercises

  1. Design (on paper, then as an OpenAPI file) a REST API for an online bookstore: resources, relationships, pagination, errors, versioning, auth. Review it against the conventions above.
  2. Implement signup, login, logout and a /me endpoint with Argon2, hashed session tokens and secure cookies. Add rate limiting to login.
  3. Write an authorization test suite (the "user B cannot access user A" matrix) for every resource endpoint.
  4. Add OAuth login (GitHub) using a library; link it to existing accounts safely.
  5. Implement an Idempotency-Key middleware backed by a table and demonstrate that retrying a POST doesn't duplicate.
  6. Generate an OpenAPI spec from your Zod schemas and a typed client for your React app (e.g., openapi-typescript).
