Lesson 72 — CI/CD, Docker & deployment

Code that isn't deployed isn't a product. Learn to build, containerize, ship and roll back automatically, so releasing becomes boring and frequent instead of rare and scary.

Docker essentials

A container packages your app with its runtime and dependencies so it runs the same everywhere. An image is the blueprint; a container is a running instance.

  • Keep images small (alpine/distroless, multi-stage), pin versions, use a non-root user, never bake secrets into images (use runtime env/secret stores).
  • Containers are ephemeral: store data in volumes or external services, log to stdout.

CI/CD pipeline

  • CI (continuous integration): every push builds and tests automatically. CD: delivery (always releasable) or deployment (every green main goes to prod automatically).
  • Pipeline stages: install (cached) → lint/typecheck → unit/integration tests → build → e2e → security scan → publish artifact/image → deploy → smoke test → notify.
  • Preview deployments per PR (Vercel/Netlify/Cloudflare) let reviewers click the real thing.

Release safety

TechniqueWhat it does
Rolling / blue-greenStart new version beside the old; shift traffic when healthy; instant rollback by shifting back
CanarySend 1–5% of traffic to the new version; watch errors/latency; ramp up or abort
Feature flagsDeploy code dark; enable per user/percentage; kill switch without redeploying
Backward-compatible migrationsExpand (add column) → deploy code that writes both → backfill → switch reads → contract (drop old). Old and new code run simultaneously during deploys
Immutable, versioned buildsEvery deploy is a tagged artifact; rollback = redeploy previous artifact
Health checks & graceful shutdownPlatform only routes to healthy instances; handle SIGTERM and drain connections

Web delivery details

  • Cache headers: Cache-Control: public, max-age=31536000, immutable for hashed assets (app.3f9a.js); no-cache (revalidate) for index.html.
  • Compression: brotli for text; correct MIME types for .wasm, .glb, .ktx2, .webmanifest.
  • HTTPS/HTTP3, HSTS, custom domain + DNS (A/AAAA/CNAME records), TLS certificates auto-managed by the host.
  • Environment config: build-time (VITE_*, public) vs runtime secrets (server only). Keep dev/staging/prod separate with their own databases and keys.
  • Infrastructure as code (Terraform, Pulumi, SST) once you outgrow clicking in dashboards.

Exercises

  1. Dockerize your Project 5 API with a multi-stage build; get the final image under ~150 MB and running as non-root; scan it with docker scout or Trivy.
  2. Write a compose file with Postgres, Redis and your API, plus a healthcheck-based startup order; document docker compose up in the README.
  3. Deploy a static 3D site to Cloudflare Pages with preview deploys per PR; set correct cache headers and verify with curl -I.
  4. Build a GitHub Actions pipeline that tests, builds an image, runs migrations, deploys, smoke-tests and rolls back automatically on failure.
  5. Practice an expand/contract migration: rename a column with zero downtime across three deploys.
  6. Put a feature behind a flag (Unleash/PostHog or a simple table), roll it out to 10% of users and then kill it.

Checkpoint

Why cache hashed assets forever but not index.html?A hashed filename changes whenever content changes, so old URLs never go stale. index.html references the current hashes, so it must be revalidated to pick up new releases.
Why must migrations be backward compatible?During a rolling deploy, old and new code run simultaneously against the same database, so schema changes must work with both versions.
