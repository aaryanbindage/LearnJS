Lesson 21 — Testing & TypeScript primer

Two skills that separate hobby code from professional code: proving it works, and letting a type checker catch mistakes before you run anything.

Testing: the idea

A test calls your code with known input and checks the output. Write pure functions and they're trivial to test. Here's a mini test framework so you can see there's no magic:

Vitest in a real project

  • Arrange → Act → Assert in every test.
  • Test behavior, not implementation details. One reason to fail per test.
  • Test pyramid: many unit tests, some integration tests, a few end-to-end tests (Playwright).
  • Mock only the boundaries (network, clock, randomness).
  • When you find a bug, first write a failing test that reproduces it.

TypeScript primer

TypeScript is JavaScript plus types, checked at build time and erased before running. It catches typos, wrong argument shapes, and missing null checks. Most React and Three.js code in the wild is TypeScript.

TipTurn on "strict": true in tsconfig.json. Avoid any; use unknown and narrow. Types at the edges (API responses, props) pay off most.

Exercises

  1. Write 6 tests for a slugify function, including edge cases (empty string, emoji, multiple spaces). Fix the function until green.
  2. Write a failing test for a bug in your to-do app, then fix it.
  3. Convert a small JS utility module to TypeScript with strict mode and fix all errors.
  4. Type an API response (Todo[]) and a generic fetchJson<T>.
  5. Model a state machine with a discriminated union: {status:"idle"} | {status:"loading"} | {status:"error", message:string} | {status:"ok", data:T}.

Checkpoint

Do TypeScript types exist at runtime?No. They're erased during compilation, so you still need runtime validation (e.g., zod) for external data.
What makes code easy to test?Pure functions with explicit inputs/outputs and dependencies passed in rather than hard-coded.
