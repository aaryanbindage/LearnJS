Real TypeScript projects & testing

So far the editors on this site have done the setup for you. Professional code lives in project folders on your computer, with a build tool, a type checker, version control and automated tests. This lesson walks you through setting all of that up, step by step, for a real TypeScript project.

In this lesson you will

  • Use the terminal, Node.js and npm to create and run a project.
  • Create a TypeScript project with Vite, and understand every file in it.
  • Understand the important tsconfig.json settings.
  • Save your work with Git.
  • Write automated tests with Vitest.

About 75 minutes. You'll need Node.js, VS Code and Git installed (see the Start here lesson).

Step 1: the terminal

The terminal (also called the command line or shell) is a text window where you type commands. Developers use it to create projects, install packages and run tools. Open one:

  • In VS Code (easiest): menu Terminal → New Terminal, or Ctrl + `.
  • Windows: "Terminal" or "PowerShell" from the Start menu. Mac: "Terminal" from Spotlight.

A few commands you'll use all the time. Type each, then press Enter:

Terminal tipsPress Tab to auto-complete file and folder names. Press ↑ to bring back the previous command. Press Ctrl + C to stop a running program (like a dev server).

Step 2: Node.js and npm

Node.js runs JavaScript outside the browser. It's what all the developer tools (TypeScript, Vite, test runners) run on. npm (Node Package Manager) comes with Node. It downloads packages: code other people have published for you to use. There are over two million of them.

Every project has a package.json file listing its packages and its commands (called scripts):

  • npm install downloads everything listed into a folder called node_modules. That folder is big and can always be re-created, so it's never shared or committed.
  • npm install some-package adds a new package. Add -D for tools only needed while developing.
  • npm run dev runs the "dev" script.
  • package-lock.json records exact versions, so everyone gets the same ones. Keep it.

Step 3: create a TypeScript project with Vite

Vite is a build tool: a development server that reloads the page instantly as you save, and a command that bundles your code for publishing. It understands TypeScript out of the box. Let's create a project. In your terminal, go to a folder where you keep projects, and run:

  1. npm create vite@latest downloads Vite's project generator and creates a folder my-ts-app from the vanilla-ts template ("vanilla" means plain TypeScript, no framework).
  2. cd my-ts-app moves into it; npm install downloads the packages.
  3. npm run dev starts the dev server. It prints an address like http://localhost:5173. Open it in your browser.

Now open the folder in VS Code (code . in the terminal, or File → Open Folder). The important files:

index.htmlThe page. It loads /src/main.ts with <script type="module">. Yes, a .ts file: Vite converts it on the fly.
src/main.tsYour code's starting point.

Try it
  1. Delete everything in src/main.ts and write document.body.textContent = "Hello from TypeScript!";. Save. The browser updates instantly.
  2. Now write const n: number = "oops";. VS Code underlines it in red, just like the editors on this site.
  3. Copy the typed to-do app from the Events lesson into main.ts (and its HTML into index.html) and get it running.

Vite doesn't check types; tsc does

Here's a detail that surprises people: to stay fast, Vite only removes types; it doesn't check them. Your editor shows errors as you type, and the build script runs the TypeScript compiler, tsc, which checks the whole project and refuses to build if anything's wrong. Step 4: tsconfig.json

This file tells TypeScript how strict to be and what kind of JavaScript to target. The template's version is good. These are the settings worth understanding:

"strict": true switches on all the checks you've been relying on in this course: parameters must have types, null and undefined must be handled, and more. Never turn it off.

noUncheckedIndexedAccess is worth a mention: with it, arr[0] has type T | undefined, because the array might be empty. It's a little more work, and catches real bugs. Add it to your project.

Step 5: save your work with Git

Git keeps a history of your project. Each time you reach a good point, you make a commit: a saved snapshot with a message. You can always go back. Vite already created a .gitignore file, which tells Git to skip node_modules and dist.

Commit small and often, with messages that say what changed. You'll learn branches and team workflows later in the course.

Step 6: automated tests

How do you know your code works? You try it. But every time you change something, you'd have to try everything again. A test is code that checks your code: it calls a function with known inputs and checks the output is what you expect. Then a computer can re-check everything in a second, every time you save.

Vitest

Vitest is a real test runner that works with Vite and TypeScript with no extra setup. Install it and add a script:

Put the code to test in its own file, and the tests in a file next to it ending in .test.ts:

  • describe groups related tests; it is one test, with a sentence saying what should happen.
  • expect(actual).toBe(expected) for simple values; .toEqual to compare the contents of objects and arrays.
  • The tests are TypeScript too, so a test that calls your function wrongly is caught by the type checker.
Good testing habits
  • Test pure functions first (same input → same output, no DOM or network). Keep your logic in functions like that, and they're easy to test.
  • Test the edge cases: empty arrays, zero, empty strings, very large values.
  • When you find a bug, first write a test that fails because of it, then fix the code. That bug can never sneak back.
  • Types and tests work together: TypeScript catches "wrong kind of value", tests catch "wrong answer".

Linting and formatting

Two more tools you'll find in almost every project. Install them as VS Code extensions too, so they work as you type:

  • ESLint finds likely bugs and bad patterns (an unused variable, a missing await). With typescript-eslint it understands types.
  • Prettier formats your code automatically on save, so you never argue about spaces again.

Recap

  • Terminal basics: cd, ls, mkdir; Tab completes, Ctrl+C stops.
  • npm install fetches packages into node_modules; npm run <script> runs package.json scripts.
  • npm create vite@latest app -- --template vanilla-ts creates a TypeScript project; npm run dev runs it.
  • Vite strips types; tsc --noEmit (and npm run build) check them. Keep "strict": true.
  • Git: git add . then git commit -m "...", often.
  • Vitest: describe, it, expect(...).toBe/toEqual in *.test.ts files; npm test.

Practice

  1. Create the Vite TypeScript project above, replace the starter code with your own "Hello" page, and commit it with Git.
  2. Move the slugify function into src/slugify.ts, export it, and write at least five Vitest tests for it, including edge cases (empty string, emoji, several spaces, capital letters). Make them all pass.
  3. Turn on noUncheckedIndexedAccess in tsconfig.json, run npx tsc --noEmit, and fix whatever it finds.
  4. Put the project on GitHub.

Check your understanding

Why isn't node_modules committed to Git?It's huge and can be re-created exactly from package.json and package-lock.json with npm install.
Does the Vite dev server stop you if you have a type error?No. Vite only strips types. Your editor, npx tsc --noEmit, and npm run build do the checking.
What's the difference between toBe and toEqual?toBe checks that two values are exactly the same (===). toEqual checks that objects or arrays have the same contents.
