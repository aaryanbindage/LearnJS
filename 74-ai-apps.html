Lesson 74 — Building AI features into web apps

LLMs are now a standard ingredient: chat, summarization, extraction, search, assistants that take actions. This lesson covers how to integrate them safely and well: backend proxying, streaming UIs, structured output, tools, retrieval and evaluation.

Architecture: never call the model from the browser with your key

  • API keys are secrets. A key in front-end code is public and will be stolen and abused. Always call the model API from your server (or a serverless function) and expose your own authenticated, rate-limited endpoint to the front end.
  • The backend also lets you add auth, per-user quotas, input validation, logging, cost tracking, caching, prompt templates and moderation.
  • Pick the model per task: a small fast model for classification/extraction, a larger one for hard reasoning. Check current model names and pricing in the provider docs; they change often. (For the Claude API, the current model ids are in Anthropic's docs; the examples here use claude-sonnet-5-5.)

The streaming chat UI

Users perceive streamed text as much faster. Read the response body as a stream and append tokens as they arrive. Try the interaction pattern below with a fake model (no network needed), then point it at your real endpoint.

  • UX details: stop button (abort), retry, copy, regenerate, empty/error states, scroll anchoring, markdown rendering (sanitize it!), loading indicators, and clearly labeling AI content.
  • Libraries: Vercel AI SDK (useChat), Anthropic/OpenAI SDKs, assistant-ui. Handle the model's partial markdown while streaming.

Structured output and tool use

For features that feed code (not just chat), have the model return validated structured data or call your functions.

Agents: the tool loop

  1. Send the user request plus tool definitions (search_orders, create_ticket, …).
  2. If the response contains a tool_use block, your server runs that function (with the end user's permissions), then sends the result back as a tool_result.
  3. Repeat until the model returns a final answer, with a max-iterations cap.
SecurityTreat model output as untrusted input. Authorize every tool call as the current user, validate arguments, require human confirmation for destructive actions, and never let retrieved text or user content override your system rules (prompt injection). Don't give an agent more privileges than the user has. Sanitize rendered output (XSS), and don't put secrets in prompts.

Retrieval-augmented generation (RAG)

Models don't know your private or fresh data. RAG fetches relevant snippets at question time and includes them in the prompt, so answers are grounded and cite sources.

  1. Ingest: split documents into chunks (~300–800 tokens with overlap), store text + metadata.
  2. Embed: convert chunks to vectors with an embeddings model; store in Postgres + pgvector (or Pinecone/Qdrant).
  3. Retrieve: embed the question, find nearest chunks (cosine similarity), optionally combine with keyword search and re-rank. Filter by user permissions in the query.
  4. Generate: prompt the model with the question + retrieved chunks, instruct it to answer only from them and cite ids; say "I don't know" when they don't contain the answer.

Prompting, cost and quality

  • Prompt as code: version prompts, keep them in files, use clear structure (role, task, constraints, examples, output format), delimit untrusted content (<document>…</document>).
  • Cost control: cap max_tokens and history length, cache identical requests, use prompt caching for long repeated context, pick smaller models where quality allows, rate limit per user, track tokens per feature.
  • Latency: stream, show progress, parallelize independent calls, pre-compute where possible.
  • Reliability: timeouts, retries with backoff on 429/5xx, fallbacks, graceful degradation when the API is down.
  • Evaluate: models are non-deterministic and change. Build an eval set of real inputs with expected properties; run it in CI on every prompt/model change; sample and review production outputs; collect thumbs up/down. Without evals you're guessing.
  • Safety and privacy: moderate inputs/outputs where needed, avoid sending unnecessary PII, check provider data-retention terms, disclose AI use, keep a human in the loop for high-stakes decisions.

AI in 3D and creative apps

  • Natural-language scene control: the model returns a validated JSON "scene command" (add object, change color) that your code applies, never raw code executed from the model.
  • NPC dialogue with strict persona prompts, token caps and content filters; image/texture generation via a server-side job queue; semantic search of asset libraries with embeddings.
  • On-device models (WebGPU with transformers.js, WebLLM) for private, offline inference when quality needs are modest.

Exercises

  1. Build the streaming chat endpoint and UI against a real model (key on the server only). Add auth, a per-user daily token quota, abort on disconnect and error states.
  2. Build an "invoice/receipt extractor": upload text, force a tool call, validate with Zod, and let the user correct fields before saving.
  3. Implement a tool-using assistant for your Project 5 app (search items, create a task) with per-user authorization, confirmation for writes and an iteration cap.
  4. Build RAG over your own notes with pgvector: chunking, embeddings, permission-filtered retrieval, citations in the UI, and an "I don't know" path.
  5. Write 30 eval cases (inputs + checks) and a script that scores outputs; run it before and after a prompt change.
  6. Red-team your feature: attempt prompt injection through user content and retrieved documents; document and fix each hole.

Checkpoint

Why proxy model calls through a backend?It keeps the API key secret and lets you enforce auth, quotas, validation, logging and cost controls. A key in the browser can be copied and abused.
Why validate tool/structured output?Model output is untrusted and sometimes malformed or manipulated. Parse it with a schema and authorize actions like any other user input.
