Lesson 78 — Reading source code & contributing to open source

The fastest way past "tutorial level" is reading real code. Documentation tells you what a library promises; the source tells you what it does. Mastery means you're never blocked by "the library doesn't do X": you can open it, understand it, and fix or extend it.

How to read an unfamiliar codebase

  1. Run it first. Clone, install, run the dev server and tests. Use it as a user before reading as a developer.
  2. Read the map: README, CONTRIBUTING, package.json (scripts, entry points, dependencies, exports), folder layout, architecture docs.
  3. Pick one behavior and trace it from entry to exit: e.g., "what happens when I call setState?" or "how does renderer.render() draw a mesh?". Follow the call path with your editor's Go to Definition and Find References, plus the debugger.
  4. Use the debugger and logs: set a breakpoint in node_modules/<lib> (source maps help), step through, inspect the call stack. It's faster than reading statically.
  5. Read the tests: they're executable documentation of intended behavior and edge cases.
  6. Read history: git log -p -- file, git blame, and the linked PRs/issues explain why weird code exists.
  7. Take notes and draw diagrams. Summarize each module in one sentence. Rewrite a simplified version yourself.

Reading Three.js

Exercise in reading: find where Object3D.updateMatrixWorld is called during render, why matrixAutoUpdate exists, and how frustum culling decides to skip an object. Then write a 100-line version of a scene graph that does the same.

Reading React (concepts, not every line)

  • Read Build your own React (Rodrigo Pombo) and "Inside Fiber" explanations first, then skim packages/react-reconciler: ReactFiberWorkLoop (render/commit phases), ReactFiberHooks (how hooks use a linked list per component), ReactChildFiber (reconciliation/keys).
  • Implement a mini-React with createElement, a fiber-ish render loop and useState in ~150 lines. You will never again wonder why hooks must be called in the same order.

Reading the platform

  • Specs and MDN: when behavior surprises you, read the spec section (HTML, DOM, CSS specs, ECMAScript), and the Web Platform Tests for what browsers actually do. caniuse.com and MDN compatibility tables for support.
  • Browser DevTools are a code-reading tool for the web: inspect any site's CSS, JS (source maps), network waterfall and storage; learn from how great sites are built.
  • Bundle inspection: source-map-explorer/vite-bundle-visualizer show what's inside your app and which dependencies are heavy.

Debugging dependencies

  • Patch temporarily with patch-package or pnpm patch while you wait for an upstream fix; link the issue in a comment.
  • Link a local checkout (npm link, pnpm link, or a workspace) to debug a library inside your app; add logs, then turn the fix into a PR.
  • Minimal reproduction: strip the problem to the smallest project/CodeSandbox/StackBlitz that shows it. 90% of the time you find your own bug while doing it; the rest, maintainers will thank you.

Contributing to open source

  1. Start small: documentation fixes, typos, clearer examples, reproducing and triaging issues, adding missing tests, "good first issue" labels. These build trust and teach the workflow.
  2. Read CONTRIBUTING and the code of conduct; search existing issues and PRs before opening anything.
  3. Discuss before big changes: open an issue/discussion describing the problem and your proposed approach. Maintainers' time is the scarce resource.
  4. Make a focused PR: one concern, tests, docs, follows the project's style and commit/PR conventions, a clear description linking the issue. Be patient and gracious with review feedback; revisions are normal.
  5. Ship your own small library once you've felt the pain of a gap: a good README, types, tests, semver, a changelog, CI publishing with provenance. Maintenance is the real work; start tiny.

Exercises

  1. Read the full source of zustand (or mitt + nanoid), then re-implement it from memory and compare. Write down three design decisions you learned.
  2. Trace renderer.render(scene, camera) in the Three.js repo with the debugger. Produce a one-page diagram of what happens, from culling to draw calls.
  3. Build a 150-line mini-React (createElement, render, useState, simple diffing) and run a counter and a todo list on it.
  4. Pick a dependency of Project 5, find a real bug or a docs gap, create a minimal reproduction, and open an issue or PR upstream.
  5. Make a documentation or test contribution to an open-source project that is merged. Keep the link in your portfolio.
  6. Publish a tiny library to npm (e.g., a typed utility or a Three.js helper) with tests, types, README and automated release.

Checkpoint

Why can't hooks be called conditionally?React identifies each hook by its call order in the component. Skipping or adding a call changes the order, so every later hook would read the wrong slot of state.
What's the best way to start contributing?Small, focused changes (docs, tests, reproductions, good-first-issues) after reading CONTRIBUTING, and discussing before large changes. This builds trust and teaches the project's workflow.
