Union types, null & narrowing

Real values aren't always one neat type. A search might find a user or nothing. An ID might be a number or a string. A request might be loading, finished or failed. This lesson teaches you how TypeScript describes "one of several things", and how your code safely works out which one it has. It's the most important TypeScript skill after the basics.

In this lesson you will

  • Write union types with |, including unions of exact values.
  • Narrow a union with typeof, === and truthiness checks.
  • Handle null and undefined safely with ?. and ?? (these are JavaScript features, useful with or without TypeScript).
  • Model things that can be in different states with discriminated unions.
  • Use unknown instead of any.

About 60 minutes. Most of this lesson is TypeScript, with JavaScript features mixed in where they belong.

Union types: "this or that"

You've already seen a few types with a | in them when hovering, like string | undefined. The | means or. A type made of several options joined with | is called a union type.

Read number | string as "a number or a string". The variable can hold either one, at different times.

Narrowing: finding out which one you have

A union creates a small problem. If a value might be a number or a string, which methods can you use on it?

TypeScript only allows what's safe for every option. Numbers don't have toUpperCase, so it's an error. The fix is to check which one you have first, using a normal JavaScript if:

This is called narrowing. Inside the if, TypeScript knows value must be a string, so the type is narrowed from number | string to just string. After the if (which returned), the only possibility left is number.

AnalogyYou're handed a wrapped present that's either a book or a mug. You can't start reading it or drinking from it yet. First you check (narrow), and once you know which it is, you use it the right way. TypeScript follows your checks and remembers what you learned.

Notice that narrowing isn't new syntax. typeof, if and === are plain JavaScript that you already know. TypeScript just reads your checks and updates the types to match.

null and undefined: the billion-dollar mistake

The most common crash in JavaScript is using something that turned out to be missing:

Cannot read properties of undefined. You'll see this error message a lot in your career. The inventor of null, Tony Hoare, later called it his "billion-dollar mistake" because of how many bugs it has caused.

TypeScript's answer is simple: null and undefined are not included in other types. A string is always a real string. If something might be missing, its type has to say so, with a union like string | undefined or User | null. And then TypeScript makes you check before using it.

1. Check with if. The clearest option when you want to do something different when the value is missing:

2. Optional chaining ?. When you just want to read something from a value that might be missing. If the left side is null or undefined, the whole thing stops and gives undefined instead of crashing. This is a JavaScript feature, so it works in plain JS too:

3. The nullish coalescing operator ?? Gives a fallback value when the left side is null or undefined. Read a ?? b as "a, or if that's missing, b". Also plain JavaScript:

?? vs ||

You might see || used for fallbacks in older code. The difference: || falls back on any falsy value, including 0 and "", which are often perfectly valid. ?? only falls back on null and undefined.

The ruleFor "use this default if it's missing", use ??. Use || only when you really mean "if it's falsy".

There's also a short way to fill in a missing value: x ??= 10 means "if x is null or undefined, set it to 10".

The ! escape hatch (use rarely)

Sometimes you know a value isn't missing, but TypeScript can't tell. Putting ! after it tells TypeScript "trust me, this isn't null or undefined":

Careful! switches off the safety check, and if you're wrong, you get the crash TypeScript was trying to prevent. Prefer an if check or ??. Reach for ! only when you're truly certain.

unknown: the safe version of any

Sometimes you genuinely don't know what type a value is, for example data from the internet or from a file. The Meet TypeScript lesson warned you off any, which switches checking off. unknown means "could be anything" but, unlike any, you must narrow it before using it:

any vs unknownany: "don't check this". unknown: "check this before you use it". Whenever you're tempted to write any, try unknown instead.
Common mistakes
  • Using || for defaults when 0 or "" are valid values. Use ??.
  • Sprinkling ! to make errors go away. Each one is a possible crash.
  • Using typeof x === "array": arrays are "object" to typeof. Use Array.isArray(x).
  • Using typeof x === "null": typeof null is "object" (a famous old JavaScript quirk). Use x === null.
  • Several booleans for one state (isLoading, hasError…). Use a discriminated union.

Recap

  • A | B is a union: a value that is A or B. Unions of exact values ("small" | "large") are great for options.
  • Narrowing: normal checks (typeof, ===, if (x), Array.isArray) make TypeScript update the type inside that branch.
  • In TypeScript, null/undefined must be part of the type to be allowed, and must be checked before use.
  • a?.b stops safely if a is missing. a ?? b uses b when a is null or undefined. Both are plain JavaScript.
  • Discriminated unions (a shared status or kind property) model states without impossible combinations. never checks every case is handled.
  • Prefer unknown over any. Avoid ! unless certain.
