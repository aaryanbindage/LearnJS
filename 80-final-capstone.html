Lesson 80 — Final capstone

Everything comes together here. You'll design, build, ship and operate one substantial product that combines HTML, CSS, JavaScript/TypeScript, React, Three.js and a real backend, and defend it like an engineer. When you finish, you won't just have completed a course; you'll have a body of work that demonstrates mastery.

The brief

Build a web product with a meaningful 3D or visual-interactive core, backed by real data and users. Choose one (or propose your own with the same scope):

  • 3D Design & Share Studio: users create and edit simple 3D scenes/products in the browser (add shapes or import glTF, materials, lights, camera), save projects to their account, share public links with a read-only viewer, and optionally co-edit in real time.
  • Spatial Data Explorer: ingest a real dataset (energy, transit, astronomy, climate), process it on the backend, and let users explore it in an interactive 3D visualization with filters, comparisons, annotations and shareable views.
  • Multiplayer Game Platform: accounts, lobby/matchmaking, an authoritative server for a small 3D game, leaderboards, replays, anti-cheat basics.
  • 3D Commerce Platform: a store with a configurator, checkout (payments in test mode), orders, admin dashboard, inventory, and AR preview.

Non-negotiable requirements

Product & UX

  1. A written product brief: target user, problem, 8+ user stories with acceptance criteria, explicit non-goals.
  2. Responsive from 320 px to ultrawide; polished empty/loading/error/offline states; consistent design system with tokens, light + dark themes and a Storybook of core components.
  3. Accessible: WCAG 2.2 AA for all non-canvas UI, keyboard-operable editor/controls, text alternatives for 3D content, reduced-motion mode. Include an accessibility statement documenting known gaps.

Front end

  1. TypeScript strict; React (Next.js or Vite) with a documented state architecture (server cache vs client store vs URL).
  2. Three.js/R3F core with a performance budget, adaptive quality, optimized assets, a custom shader or material effect, and clean resource disposal.
  3. At least one advanced platform capability: Web Worker/OffscreenCanvas, service worker + offline, WebXR, WebGPU compute, or audio.

Back end & data

  1. PostgreSQL with migrations, constraints, justified indexes; typed data layer; seed data and an ERD.
  2. Authenticated multi-user API with validation, consistent errors, pagination, rate limiting and per-resource authorization tests.
  3. One real-time or background-processing feature (WebSocket/SSE/CRDT or a job queue) with failure handling.
  4. Object storage for user assets with presigned uploads and size/type limits.

Quality, security & operations

  1. Tests at every layer: unit (logic), integration (API + real DB), component (MSW), E2E (3+ Playwright journeys), plus automated a11y checks. CI blocks merges on failures.
  2. Security review documented: threat model, CSP, cookie/session design, CSRF strategy, dependency/secret scanning, an authorization matrix.
  3. Observability: structured logs with request ids, error tracking with source maps, RUM web vitals + FPS buckets, one dashboard and two alerts tied to SLOs.
  4. Deployed with CI/CD, preview environments, zero-downtime migrations, health checks, backups with a tested restore, and a rollback you've actually performed.
  5. Performance: Lighthouse ≥ 90 on content pages; documented budgets for bundle size, draw calls, memory; before/after evidence for at least three optimizations.

Optional stretch (choose two for distinction)

  • An AI feature built safely (“Building AI features into web apps”) with evals; WebXR mode; WebGPU/TSL compute effect; offline-first sync with conflict resolution; i18n with RTL; plugin/extension API; load test results at 500 concurrent users; accessibility test with a real assistive-technology user.

Deliverables

  1. Live app URL and a seeded demo account.
  2. Repository with clean history, README (setup in < 5 min via docker compose), architecture diagram, ERD, ADRs for ≥ 5 key decisions, CONTRIBUTING.
  3. Case study (portfolio page): the story, trade-offs, metrics, failures and lessons.
  4. 5-minute demo video: product tour, one deep technical dive, and a look at monitoring/CI.
  5. Postmortem-style retrospective: what went wrong, what you'd redo, what you'd build next.

Defend it: the final review

Present to a peer, mentor or community (or record it). Prepare to answer, with evidence:

  • Walk me through the architecture. Why these choices, and what did you reject?
  • Show me the slowest thing, how you measured it, and what you did.
  • How does a user's data stay private? Show the authorization tests.
  • What happens when the database, a third-party API or the WebSocket goes down?
  • Deploy a small change live and roll it back.
  • If traffic grew 100×, what breaks first and what's your plan?
  • What are you least proud of, and how would you fix it?
Finish lineYou're done when a stranger can open your link, use the product, find it fast and accessible, and a senior engineer can open the repo and trust it. After that, keep going: ship the next thing, read the next codebase, help someone else learn. That loop is mastery.

Final reflection

Questions to write about in your retrospective
  • Which decision saved the most time? Which cost the most?
  • Where did my estimates fail, and why?
  • What would I automate or test earlier next time?
  • What did I learn that this course didn't teach me, and what should I learn next?
