Structural typing: shapes, not names

In many languages, a value is only a Point if it was created as a Point. TypeScript doesn't care where a value came from. It only checks the shape: if it has the required properties with the right types, it fits. This is called structural typing (or "duck typing": if it walks like a duck and quacks like a duck…).

Why the difference? When you write a fresh object straight into a call, an extra property is almost always a typo ({ x: 1, yy: 2 }), so TypeScript flags it. A variable might be used elsewhere for other things, so extra properties are fine. It's a typo-catcher, not a rule about shapes.

Tuples: fixed-length arrays

A tuple is an array with a fixed length, where each position has its own type. You've used one: Object.entries returns [string, value] pairs, and React's useState returns a tuple.

Intersections: combining types with &

A union A | B is "A or B". An intersection A & B is "A and B": a value with everything from both.

type vs interface, revisitedBoth can describe objects. interface uses extends to combine; type uses &. Only type can name unions, tuples and other non-object types. Interfaces with the same name in the same scope merge together, which is how libraries let you add to their types. Rule of thumb: use type by default, and interface when you want that merging or prefer the style. Be consistent.

Common mistakes
  • as on external data: it's a promise, not a check. Validate.
  • Annotating everything: let inference work inside functions; annotate parameters, return types of exported functions, and empty starting values.
  • Trusting index signatures: turn on noUncheckedIndexedAccess.
  • Reaching for enum by habit: a string-literal union is usually simpler.

Recap

  • TypeScript is structural: any value with the right shape fits. Extra properties are only flagged on fresh object literals.
  • Tuples ([string, number]), intersections (A & B), index signatures ({ [k: string]: V }).
  • as const keeps exact values; satisfies checks without widening.
  • Prefer literal unions over enum. Prefer guards, assertion functions or zod over as.
  • Libraries ship .d.ts types, or you install @types/name.

Why can you pass {x, y, label} in a variable but not as a literal to a function expecting {x, y}?Fresh object literals get an extra "excess property" check, because extra keys there are usually typos. Values in variables are only checked for the required shape.
What's the difference between const x: T = ... and const x = ... satisfies T?The annotation makes x have type T. satisfies checks the value matches T, but x keeps its more precise inferred type.
Why is data as User risky for API data?It doesn't check anything at runtime. If the data has a different shape, your code crashes later in a confusing place. Validate instead (type guard, assertion function, zod).
