Lesson 75 — Clean code, refactoring & technical debt

Code is read far more often than it is written. The goal isn't cleverness; it's code that the next person (usually you in three months) can understand and change safely.

Naming and structure

  • Names reveal intent: isOverdue(invoice) beats check(i). Booleans read as questions (hasAccess), functions as verbs (fetchUser), collections as plurals. Avoid abbreviations and noise words (data, info, manager).
  • Small functions that do one thing at one level of abstraction. If you need a comment to explain a block, extract it into a well-named function.
  • Few parameters (≤ 3); pass an options object beyond that. Avoid boolean flag parameters (render(true, false)); split into two functions or use named options.
  • Early returns flatten nesting. Pure functions where possible; isolate side effects at the edges.
  • Comments explain why (constraints, trade-offs, links), not what. Delete commented-out code (Git remembers).

Principles worth keeping

  • DRY, but not at any cost: duplication is cheaper than the wrong abstraction. Wait for the third occurrence ("rule of three") and make sure the pieces change for the same reason.
  • KISS / YAGNI: build what's needed now. Speculative generality (config for features nobody asked for) is debt.
  • SOLID in spirit: single responsibility, depend on abstractions at boundaries, prefer composition. Don't turn it into ceremony.
  • Make illegal states unrepresentable (“TypeScript in depth: modeling real data”). Fail fast with clear errors at boundaries.
  • Separation of concerns: UI, state, data access, business rules. Command–query separation: functions either do something or return something.
  • Law of Demeter: talk to your direct collaborators (order.total()), not through chains (order.customer.address.country.code).
  • Immutability and explicit dependencies make code predictable and testable.

Refactoring safely

  1. Have tests first. If none exist, write characterization tests that pin current behavior (even if ugly), then refactor under their protection.
  2. Tiny steps, each leaving tests green. Commit often; separate refactor commits from behavior changes.
  3. Lean on tools: IDE rename/extract/move (they update references safely), TypeScript compiler errors as a to-do list, codemods (jscodeshift, ast-grep) for large mechanical changes.
  4. Strangler pattern for big rewrites: build the new path beside the old, route traffic gradually, delete the old when empty. Avoid "big bang" rewrites; they often fail.
  5. Boy-scout rule: leave code a little cleaner than you found it, in the area you're already changing.

Technical debt

  • Debt is a trade-off: deliberately shipping a shortcut to learn or hit a date is fine if recorded and repaid. Accidental, unacknowledged debt is what kills velocity.
  • Make it visible: track debt items in the backlog with impact ("slows every checkout change by a day") rather than vague "cleanup". Reserve capacity (~10–20%) for it.
  • Prioritize by pain: pay down debt in code that changes often (hot spots: check git log churn × complexity), ignore stable ugly code nobody touches.
  • Dependencies are debt: update regularly in small increments (Renovate/Dependabot), not once every two years; remove unused ones.
  • Explain debt to non-engineers in terms of delivery speed, risk and cost.

Documentation and readability for teams

  • A good README is your best onboarding tool: purpose, quick start, architecture sketch, common commands, how to test and deploy.
  • Prefer types, tests and naming over prose that rots. Use ADRs for decisions and JSDoc/TSDoc for public APIs (the "why", edge cases, examples).
  • Automate style: Prettier + ESLint, so reviews focus on design. Keep consistent patterns across the codebase; consistency beats personal preference.

Exercises

  1. Take the worst function from one of your earlier projects. Write characterization tests, then refactor it in small commits to meet the guidelines above. Compare before/after complexity (ESLint complexity rule).
  2. Split a 300-line React component into components + custom hooks; show that the tests still pass and the render behavior is unchanged.
  3. Replace a big switch on type with a discriminated union and an exhaustive check; add a new case and watch the compiler guide you.
  4. Find hot spots in a repo: git log --format=format: --name-only | sort | uniq -c | sort -rn | head; pick one and list concrete refactors.
  5. Use a codemod (jscodeshift or ast-grep) to apply a mechanical change across a project (e.g., rename an API, convert var to const).
  6. Write an ADR and a tech-debt ticket (with impact and proposed fix) for something in your own code.

Checkpoint

Why write tests before refactoring?Refactoring means changing structure without changing behavior. Tests are how you know behavior stayed the same.
When is duplication better than abstraction?When the duplicated code changes for different reasons. A wrong abstraction couples unrelated things and is harder to undo than copied code.
