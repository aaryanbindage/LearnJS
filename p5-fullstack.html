Project 5 — A production full-stack application

Build, test, secure and deploy a complete multi-user product with a database, authentication, real-time features and a polished front end. The goal is an app you'd be comfortable showing to an employer or giving to real users.

Pick a product

  • Team task board: workspaces, invitations and roles, boards/columns/cards, drag-and-drop, comments, live updates, activity feed.
  • Booking platform: providers publish availability; customers book slots; double-booking prevention with transactions; email confirmations; calendar view.
  • Mini store: catalog, search, cart, checkout with Stripe test mode, order history, admin dashboard, inventory.
  • Collaborative notes/whiteboard: documents, sharing permissions, real-time cursors and CRDT sync, version history.

Requirements

Product

  1. At least 6 user stories written down with acceptance criteria before coding; a README "product spec".
  2. Multi-user with sign up / login / logout / password reset (or passkeys/OAuth) and roles + ownership-based authorization.
  3. At least one real-time feature (live updates, presence, or notifications).
  4. At least one background job (email, image processing, report generation, webhook handling) with retries.

Architecture

  1. Next.js (or React + Fastify/Hono) with TypeScript strict; PostgreSQL with migrations and seed data; Prisma or Drizzle.
  2. Zod schemas shared for validation and types. Consistent error format. Pagination everywhere lists can grow.
  3. Clear layering: UI → actions/routes → services → repositories. No business logic in components.
  4. Environment config validated at startup; no secrets in the repo.

Quality

  1. Security: parameterized queries, output encoding, CSP (report-only is the minimum), secure cookies, CSRF protection, rate limiting, per-resource authorization tests, dependency audit passing.
  2. Testing: unit tests for services, API integration tests with a real test database, component tests, and 3+ Playwright end-to-end flows (including auth and a permission failure).
  3. Accessibility: Lighthouse a11y ≥ 95, axe tests, keyboard-only walkthrough documented.
  4. Performance: indexes justified by EXPLAIN; no N+1; Lighthouse mobile ≥ 85; bundle analysis noted.
  5. Observability: structured logs with request ids, error tracking (Sentry or similar), a /health endpoint.

Delivery

  1. CI (GitHub Actions): lint, typecheck, test, build on every PR; migrations applied automatically on deploy.
  2. Deployed to a public URL with a managed Postgres, HTTPS, environment variables and backups configured.
  3. README: architecture diagram, ERD, setup in under 5 minutes (docker compose up), decisions and trade-offs, known limitations.

Milestones (≈ 2 weeks)

  1. Days 1–2: spec, wireframes, ERD, repo, CI skeleton, database + migrations, auth.
  2. Days 3–5: core CRUD with authorization, validation and tests; seed data.
  3. Days 6–7: real-time feature and background job.
  4. Days 8–9: UI polish, responsive design, accessibility, empty/loading/error states.
  5. Days 10–11: security hardening pass, performance pass, E2E tests.
  6. Days 12–14: deployment, monitoring, documentation, demo recording, fixes from a peer review.

Starter commands

Self-review

Questions a senior reviewer would ask
  • Show me the test proving user A can't touch user B's data.
  • What happens if two users do X at the same moment? (transactions, constraints, version checks)
  • Where would this break first at 100× the traffic, and how would you know?
  • How do I run, migrate, back up and restore this app?
  • What did you consciously leave out, and why?
