Lesson 67 — WebGPU, TSL & compute

WebGPU is the successor to WebGL: lower overhead, modern GPU features and, crucially, compute shaders, which let the GPU run general-purpose parallel work (simulating a million particles, cloth, fluids, culling). Three.js supports it through WebGPURenderer and a JavaScript shader language called TSL.

Moving targetThe Three.js WebGPU renderer and TSL are evolving, and import paths, node names and defaults have changed between releases. Pin your Three.js version, read the official webgpu_* examples for that version, and treat the code below as the shape of the API rather than copy-paste truth.

WebGL vs WebGPU

Check support: if (navigator.gpu) …. Three's WebGPURenderer automatically falls back to a WebGL2 backend when WebGPU is unavailable (with some features, like compute, limited there).

Setting up the WebGPU renderer

TSL: write shaders in JavaScript

TSL (Three Shading Language) builds a shader graph from ordinary JS function calls. The same code compiles to WGSL (WebGPU) or GLSL (WebGL fallback). Composition is easy: functions are reusable and mix with built-in material nodes, so you rarely patch strings.

  • Node materials expose slots (colorNode, positionNode, normalNode, emissiveNode, opacityNode…) instead of raw gl_FragColor.
  • Control flow in TSL uses If, Loop, select (functions), not JS if (which runs on the CPU while building the graph).

Compute shaders: a GPU particle system

Particles live in storage buffers on the GPU. A compute pass updates all of them in parallel each frame, then the render pass draws them. No CPU loop, no per-frame uploads, so a million particles are practical.

What compute unlocks

  • Massive particle/boid systems, fluid and smoke (grid simulations), cloth and soft bodies, GPU culling and LOD selection, skinning of crowds, procedural terrain generation and mesh building, image processing, and even small ML inference.
  • Workgroups: compute runs threads in groups with fast shared memory; coordinate with barriers for reductions, prefix sums and sorting. Race conditions are possible: two threads writing the same element needs atomic operations.
  • Reading back to the CPU (getArrayBufferAsync) is slow and asynchronous; keep data on the GPU and render directly from it.

Raw WebGPU (to understand what's underneath)

Strategy: when to adopt

  • Shipping to the general public today: Three.js with WebGLRenderer is the safe default. Use WebGPU/TSL for new projects where you need compute or want a forward-looking codebase, and test the fallback path.
  • Feature-detect and degrade gracefully (fewer particles, simpler materials) rather than blocking users.
  • Other WebGPU engines/libraries: Babylon.js (mature WebGPU), PlayCanvas, wgpu (Rust/WASM), TensorFlow.js/ONNX Runtime Web backends, WebLLM.

Exercises

  2. Port the “Advanced shaders: SDFs, raymarching, GPGPU” displaced-fresnel material to a MeshStandardNodeMaterial with TSL nodes.
  3. Build a GPU particle fountain (compute): emit, apply gravity and floor bounce, recycle dead particles. Show the FPS at 100k, 1M and 5M.

  5. Add feature detection so your app uses WebGPURenderer when available and otherwise a simpler WebGL scene; test by disabling WebGPU in browser flags.
  6. Implement Conway's Game of Life with ping-pong storage buffers in compute and render the grid as a texture.

Checkpoint

What can WebGPU do that WebGL cannot?Run compute shaders (general GPU programs with storage buffers and shared memory), plus lower-overhead explicit pipelines, enabling simulations and culling entirely on the GPU.
Why is TSL useful?You write shader logic once in JavaScript; Three compiles it to WGSL or GLSL depending on the backend, and it composes with built-in node materials instead of string-patching shader code.
