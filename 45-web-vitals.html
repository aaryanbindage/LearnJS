Lesson 45 — SEO, performance & Core Web Vitals

Fast pages convert better, rank better and work on cheap phones and slow networks. Performance is measured with real metrics, not feelings.

Core Web Vitals

MetricMeasuresGood
LCP Largest Contentful PaintLoading: when the main content appears≤ 2.5 s
INP Interaction to Next PaintResponsiveness: delay from input to visual response≤ 200 ms
CLS Cumulative Layout ShiftVisual stability: unexpected movement≤ 0.1

Others: TTFB (server response), FCP, TBT (lab proxy for INP). Thresholds are measured at the 75th percentile of real users. Check current definitions at web.dev/vitals.

Lab data (Lighthouse, WebPageTest) is reproducible for debugging. Field data (CrUX, your own RUM via the web-vitals library) shows what real users experience. You need both.

Improving LCP (loading)

  1. Fast server: CDN, caching (Cache-Control), compression (Brotli), HTTP/2/3, SSR/SSG instead of client-only rendering for content.
  2. Prioritize the hero resource: <img fetchpriority="high">, <link rel="preload" as="image">; never lazy-load the LCP image.
  3. Right-size images: AVIF/WebP, srcset/sizes, correct dimensions.
  4. Cut render-blocking: inline critical CSS, defer scripts, avoid giant CSS bundles, no blocking third-party scripts.
  5. Fonts: self-host, woff2, subset, font-display: swap, preload the key font, use size-adjust fallback to reduce shifts.

Improving INP (responsiveness)

Long tasks (> 50 ms) on the main thread block input. Break them up.

  • Yield with scheduler.yield() (fallback setTimeout), move heavy work to a Web Worker, debounce handlers, use requestIdleCallback for non-urgent work.
  • In React: useTransition/useDeferredValue, virtualize long lists, avoid re-rendering huge trees, code-split.
  • Reduce JavaScript: audit bundles, remove unused dependencies, lazy-load below-the-fold widgets, defer third-party tags.

Improving CLS (stability)

  • Always set width/height (or aspect-ratio) on images, video and iframes.
  • Reserve space for ads, embeds and late-loaded content with min-height/skeletons.
  • Don't insert content above existing content after load; animate with transform, not layout properties.
  • Avoid font swap jumps (matching fallback metrics).

The JavaScript budget

Rough budget for good mobile experience: under ~170 KB of compressed JavaScript for the initial route. Code-split routes, import only what you use, and prefer platform features (Intl, fetch, structuredClone, CSS) over libraries.

SEO essentials

  • Crawlable content: important text must be in the HTML a crawler receives. Use SSR/SSG for content sites; client-only SPAs risk delayed or incomplete indexing.
  • Per-page <title> (≈ 50–60 chars), <meta name="description">, one h1, logical headings, descriptive link text, alt text, canonical URL.
  • Social cards: Open Graph and Twitter tags.
  • Structured data (JSON-LD) for rich results; sitemap.xml, robots.txt; clean, stable URLs; correct status codes (404 vs 200); HTTPS; mobile-friendly; fast.

Performance for 3D pages

Don't ship a 20 MB model on first paint. Show real HTML content and a poster image immediately, lazy-load the WebGL scene after the main content (IntersectionObserver or requestIdleCallback), and treat the 3D as an enhancement. LCP should be text/image, not the canvas.

Measure like a professional

  1. Lighthouse (mobile, throttled) for a first look; WebPageTest for waterfalls and filmstrips on real devices.
  2. Chrome DevTools Performance panel: record the interaction, find long tasks and layout thrash.
  3. Network panel with throttling ("Slow 4G") and CPU throttling (4–6× slowdown).
  4. CrUX / PageSpeed Insights field data; RUM via web-vitals.
  5. Performance budgets in CI (Lighthouse CI, size-limit).

Exercises

  1. Run Lighthouse on your Project 3 app; list the top 5 opportunities; fix at least 3 and re-measure.
  2. Find your LCP element in DevTools and make it load faster (priority hints, right-sized AVIF).
  3. Trigger an INP problem (a 300 ms handler), find it in the Performance panel, then fix it by yielding or a worker.
  4. Eliminate every layout shift on a page (use the "Layout Shift Regions" rendering option).
  5. Add web-vitals reporting to a small backend endpoint and chart the numbers.
  6. Add a size budget (size-limit) to CI so a PR fails if the bundle grows too much.

Checkpoint

Why not lazy-load the hero image?The hero is usually the LCP element. Lazy-loading delays its fetch until layout, hurting LCP. Load it eagerly with high priority.
Lab vs field data?Lab is controlled and reproducible for debugging; field is what real users on real devices and networks experience, and is what Google uses for ranking signals.
