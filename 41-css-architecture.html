Lesson 41 — CSS architecture: BEM, layers & modules

CSS is easy to write and hard to maintain. At scale the problems are specificity wars, global leakage and dead code. Architecture is how you prevent them.

The three problems

  1. Global scope: every selector can affect every element.
  2. Specificity: later changes need ever more specific selectors or !important.
  3. Dead code: nobody dares delete a rule because they can't tell who uses it.

Every strategy below trades off these three.

Strategy 1: naming conventions (BEM)

Block__Element--Modifier. A block is a standalone component, an element is a part of it, a modifier is a variation. One class per rule keeps specificity flat (0-1-0).

  • Never style an element by its tag inside a block (.card h2); give it a class.
  • Don't chain blocks: .card__header__title is wrong; use .card__title.
  • Pros: no tooling, readable HTML. Cons: long names, discipline required.

Strategy 2: cascade layers

@layer lets you declare priority order up front, independent of specificity or source order. A rule in a later layer beats an earlier layer, even if the earlier selector is more specific. Unlayered styles beat all layers.

Use layers to tame third-party CSS: @import url(lib.css) layer(vendor); puts a library in the lowest layer so your own CSS always wins.

Strategy 3: scoping (CSS Modules, CSS-in-JS, @scope)

  • CSS Modules: build-time scoping, plain CSS, zero runtime. Built into Vite/Next.js. Excellent default for React.
  • CSS-in-JS (styled-components, Emotion): dynamic styles from props, but runtime cost and trouble with Server Components. Zero-runtime options: vanilla-extract, Panda CSS, Linaria.
  • Native @scope: @scope (.card) to (.card__content) { img { border-radius: 8px } } styles only inside a boundary. Check browser support before relying on it.
  • Utility-first (Tailwind): next lesson.

Design tokens

Put every design decision in custom properties once; components only reference tokens. Use two tiers: primitive (--blue-500) and semantic (--color-action). Re-theming changes only the semantic mapping.

Typed custom properties: @property --angle { syntax: "<angle>"; inherits: false; initial-value: 0deg; } makes custom properties animatable.

Organizing files

Useful tiny layout primitives (from "Every Layout"): .stack (vertical rhythm via > * + * { margin-block-start: var(--space) }), .cluster (wrapping flex row), .sidebar, .grid-auto. They replace hundreds of one-off rules.

Tooling for CSS quality

  • Stylelint: lints CSS (no duplicate selectors, bad values, enforce ordering).
  • PostCSS / Lightning CSS: autoprefixing, nesting, minification (Vite uses Lightning CSS or PostCSS).
  • Coverage panel in Chrome DevTools: shows unused CSS.
  • Visual regression tests (Playwright screenshots, Chromatic) catch unintended style changes.

Exercises

  1. Refactor your Project 1 portfolio into tokens.css, base.css and component files using layers. Remove every !important and id selector.
  2. Write a BEM-named .media-object component with two modifiers, then re-implement it as a CSS Module.
  3. Build a theme switcher with three themes by changing only semantic tokens.
  4. Wrap a third-party CSS library in a low-priority layer and prove your overrides win without raising specificity.
  5. Use the DevTools Coverage tab on a real site and report what percentage of CSS is unused.

Checkpoint

How do layers differ from specificity?Layer order is evaluated before specificity. A low-specificity rule in a later layer beats a high-specificity rule in an earlier layer.
Why prefer flat, single-class selectors?Equal specificity means source order or layer order decides, making overrides predictable and refactors safe.
