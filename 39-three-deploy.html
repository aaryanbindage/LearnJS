Lesson 39 — Performance, deployment & production

A 3D site that runs at 120 FPS on your desktop but 8 FPS on a phone is a failed site. Learn to measure, budget, optimize, and ship.

Find the bottleneck first

SymptomLikely causeFix

Crash on mobileGPU memory exhaustedSmaller textures, dispose, fewer render targets

Measure

Set budgets up front, e.g. < 100 draw calls, < 500k triangles, < 5 MB initial 3D payload, 60 FPS on a mid-range phone.

Optimization checklist

Rendering

  • Cap pixel ratio. Consider dynamic resolution: lower DPR when FPS dips (PerformanceMonitor in drei).
  • Merge static geometry (BufferGeometryUtils.mergeGeometries) and use InstancedMesh for repeats.
  • Share geometries and materials across meshes. Fewer unique materials = fewer state changes.
  • Prefer baked lighting (lightmaps/AO maps) and an environment map over many real-time lights. Limit shadow-casting lights; bake static shadows.
  • Frustum culling is on by default; add LOD (THREE.LOD) for far objects. Avoid transparency where possible (sorting and overdraw).
  • Render on demand when nothing animates (frameloop="demand" in R3F; or stop setAnimationLoop when idle/hidden).

JavaScript

  • No allocations in the loop: hoist new Vector3() out, use .set()/.copy().
  • Don't raycast every frame against everything; use bounding volumes or BVH.
  • Offload heavy computation to Web Workers; render with OffscreenCanvas if the main thread is busy.

Assets

  • Compress: Draco/Meshopt for geometry, KTX2 (Basis) for textures. Resize textures to what's visible (1k–2k, rarely 4k).
  • Lazy-load heavy scenes below the fold (IntersectionObserver), show a poster image or placeholder first.
  • Always dispose() geometries, materials, textures and render targets you drop.

Robust production behavior

Accessibility & UX for 3D

  • A canvas is invisible to screen readers: provide text alternatives, real HTML content for important information, keyboard controls, and a pause button for motion.
  • Show a loader; never present a blank canvas. Provide a still fallback when WebGL isn't available.
  • Don't hijack scroll without need; keep standard controls discoverable.

Build and deploy

  • Hosting: Netlify, Vercel, Cloudflare Pages, GitHub Pages (static). Put big assets on a CDN with long cache headers and gzip/brotli.
  • Serve .glb, .ktx2, .hdr with correct MIME types and cross-origin headers if on another domain (CORS).
  • Draco/Basis decoders: host them with your app (copy from three/examples/jsm/libs/draco and basis) and point loaders at them.
  • Tree-shaking: import { Mesh, BoxGeometry } from "three" helps bundlers; most of Three is still included but this is fine for most projects.
  • Set <meta name="viewport"> and touch-action: none on the canvas if you handle gestures yourself.
  • Analytics for performance: sample FPS and device info (GPU via WEBGL_debug_renderer_info, sparingly) to see real-world problems.

  • WebGPU (WebGPURenderer, TSL): next-generation graphics and compute on the web.

Checkpoint

Why are draw calls such a common bottleneck?Each draw call has CPU-side overhead (state setup, validation). Thousands of separate meshes exceed what the CPU can submit per frame, even if the GPU is idle.
What must you do when removing objects from the scene?Remove them, then dispose geometries, materials and textures; otherwise GPU memory leaks until the page is closed.
