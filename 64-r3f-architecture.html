Lesson 64 — React Three Fiber architecture

React Three Fiber (R3F) is a React renderer for Three.js: JSX elements map to Three objects, and React's state and component model manage the scene. Used well, it scales to large apps. Used carelessly, it re-renders at 60 fps and tanks performance. This lesson is about the right structure. The snippets need a Vite or Next.js project with three, @react-three/fiber and @react-three/drei.

How R3F maps to Three.js

  • Lowercase JSX tags are Three classes (<mesh> → new THREE.Mesh()). args feed the constructor; changing args recreates the object.
  • Pierced props: position-x={1}, rotation={[0, Math.PI, 0]}. Events (onClick, onPointerOver) use raycasting and bubble through the scene graph.
  • <Canvas> creates its own React root; context does not cross it. Re-provide any context inside, or use Zustand stores.

The one rule: never put frame-rate data in React state

WrongRight
const [x,setX]=useState(0); useFrame(()=>setX(x=>x+.01)) re-renders React 60×/secuseFrame((_,dt)=>{ ref.current.position.x += dt }) mutates the Three object directly
Passing position={[x, y, z]} from changing state each frameKeep rapidly changing values in refs or a store accessed with getState() inside useFrame
Creating new THREE.Vector3() inside useFrameAllocate once outside (module scope or useMemo) and reuse: no GC churn

State architecture: React for structure, store for runtime

  • HTML UI outside the Canvas (menus, HUD) reads the same store. For labels in 3D use drei's <Html> sparingly (each is a DOM node).
  • Scene graph as components: <Level>, <Player>, <Enemy id>. Data (entities) lives in the store; components render them.
  • Reuse geometries and materials: define once (useMemo or module scope) and share across many meshes. Use <Instances> / InstancedMesh for hundreds or thousands of copies.

Render loop control and performance

  • Check renderer.info (draw calls, triangles, textures). Target < 100–200 draw calls on mobile. Merge static geometry, instance repeated objects, atlas textures, compress with KTX2/Basis.
  • Dispose GPU resources you create manually (R3F auto-disposes objects it created when unmounted; shared/cached assets stay).
  • Don't conditionally mount heavy components during interactions; precompile with <Preload all /> or gl.compile() to avoid hitches.

Structuring a real app

Exercises

  1. Rebuild the Lesson 36 scene in R3F: lights, shadows, orbit controls, a clickable object that changes color via a store.
  2. Take a version that uses setState in useFrame, profile it with the React Profiler, then refactor to refs and show the render count drop.
  3. Render 5,000 animated cubes with <Instances> and update them in useFrame; display draw calls with r3f-perf.
  4. Load a glTF with gltfjsx --transform, make individual parts clickable and recolor materials through leva.
  5. Build a product configurator: HTML color/option pickers (outside Canvas) update 3D materials through a shared store; add frameloop="demand".
  6. Add PerformanceMonitor to downgrade DPR and shadows automatically when FPS drops; test with CPU/GPU throttling.

Checkpoint

Why avoid setState inside useFrame?It triggers a React re-render every frame. Mutating Three objects through refs (or reading a store with getState) updates the scene without React's reconciliation cost.
Why doesn't React context work inside Canvas?Canvas renders in a separate React reconciler/root, so providers outside it aren't visible within it; re-wrap the providers inside or use a store.
