Lesson 44 — Accessibility deep dive

Accessibility (a11y) isn't a feature; it's a quality bar and often a legal requirement. About one in six people live with a disability, and everyone has temporary and situational limits (a broken arm, bright sun, a noisy train).

POUR: the four principles (WCAG)

PrincipleMeaningExamples
PerceivableUsers can sense the contentalt text, captions, contrast ≥ 4.5:1, don't rely on color alone, resizable text
OperableUsers can operate controlsfull keyboard access, no keyboard traps, enough time, no seizure-inducing flashing, 24×24px minimum targets
UnderstandableContent and UI behave predictablyclear labels and errors, consistent navigation, lang
RobustWorks with assistive techvalid semantic HTML, correct roles/names/states

Target WCAG 2.2 level AA. Automated tools catch roughly a third of issues; the rest needs manual testing.

The accessibility tree: name, role, state

Browsers build a parallel tree for assistive tech. Every interactive element needs a role (what it is), an accessible name (what it's called), and state (expanded, checked, disabled). Inspect it in DevTools → Elements → Accessibility.

Rules of ARIA

  1. Don't use ARIA if a native element does the job (<button>, <details>, <dialog>, <input type="checkbox">).
  2. Don't change native semantics unless you really must.
  3. All interactive ARIA controls must be keyboard-operable.
  4. Don't use role="presentation" or aria-hidden="true" on focusable elements.
  5. All interactive elements need an accessible name.

Common useful ARIA: aria-label, aria-labelledby, aria-describedby, aria-expanded, aria-controls, aria-current="page", aria-live, aria-invalid, aria-busy, role="alert|status|dialog|tablist|tab|tabpanel".

Keyboard and focus management

  • Natural tab order follows DOM order. Never use tabindex > 0. Use tabindex="0" to make a custom widget focusable and -1 for programmatic focus.
  • Always show focus: style :focus-visible clearly (3:1 contrast against surroundings).
  • Move focus deliberately when content changes: open a modal → focus inside; close → return to the trigger; route change in an SPA → focus the new page's h1 or announce it.
  • Trap focus only inside modals. Prefer native <dialog>.showModal(), which handles the trap, Escape, and inert background.
  • Use inert on regions that should be unreachable.

Live regions: announce changes

  • role="status"/aria-live="polite" waits for the user to pause; role="alert"/assertive interrupts (errors only).
  • The live region must exist before its text changes; injecting both at once is often not announced.

Forms that work for everyone

  • Visible <label> for every field; group radios in <fieldset><legend>.
  • Connect help and error text with aria-describedby; set aria-invalid="true" on errors; say what went wrong and how to fix it.
  • Use correct type and autocomplete tokens (email, one-time-code, street-address).
  • On submit errors, move focus to an error summary or the first invalid field.
  • Don't rely on placeholder as label. Don't block paste in password fields.

Designing for diverse needs

  • Zoom and reflow: usable at 400% zoom without horizontal scroll (use rem, flex/grid, no fixed heights).
  • Motion: respect prefers-reduced-motion; provide pause for auto-playing content; avoid parallax for vestibular sensitivity.
  • Color: contrast for text (4.5:1; large 3:1) and UI components (3:1). Test forced-colors (Windows High Contrast): @media (forced-colors: active).
  • Touch: targets ≥ 24px (aim for 44px) with spacing. Provide alternatives to drag-only gestures.
  • Cognitive: plain language, consistent patterns, don't time out silently, allow undo.
  • Media: captions for video, transcripts for audio, audio descriptions where needed.

Accessible 3D and canvas

A <canvas> is a picture. For WebGL/Three.js: put essential content in real HTML, give the canvas role="img" with an aria-label (or a hidden text description), make interactive objects reachable through an HTML list or buttons that mirror them, offer keyboard controls, and provide a "pause animation" control.

Testing workflow

  1. Automated: ESLint jsx-a11y, axe-core (vitest-axe, @axe-core/playwright), Lighthouse, Pa11y in CI.
  2. Keyboard: unplug the mouse; can you do every task? Is focus always visible and logical?
  3. Screen reader: VoiceOver (macOS Cmd+F5) with Safari; NVDA (Windows, free) with Firefox/Chrome; check key flows.
  4. Zoom to 200–400%, test text spacing, forced colors, reduced motion, dark mode.
  5. Real users with disabilities, when possible. Nothing replaces this.

Exercises

  1. Audit one of your earlier projects with Lighthouse, axe DevTools, keyboard-only and VoiceOver. Write a prioritized list of issues, then fix them.
  2. Build an accessible disclosure (accordion), a tab set (arrow-key navigation, roving tabindex) and a menu button following the WAI-ARIA Authoring Practices patterns (w3.org/WAI/ARIA/apg).
  3. Make a form with inline validation that announces errors via a live region and moves focus to a summary on failed submit.
  4. Implement an SPA route change that updates document.title, moves focus to the h1 and announces the navigation.
  5. Make a Three.js scene usable by keyboard and screen-reader users: HTML list of objects, key controls, a description, and a motion toggle.
  6. Add axe checks to your test suite and fail the build on violations.
