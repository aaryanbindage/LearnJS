Lesson 61 — Advanced state & architecture

As apps grow, the hard problems are not components but state: where it lives, who owns it, how it stays consistent, and how it survives the network.

The most common architecture mistake is putting server data into a global client store and manually syncing it. Use a query cache for server state and keep your store small.

TanStack Query in depth

  • Query keys are dependency arrays for data; structure them hierarchically so invalidation can target subtrees.
  • staleTime (how long data is "fresh") vs gcTime (how long unused data stays cached).
  • Infinite scroll: useInfiniteQuery. Prefetch on hover/route-intent. Hydrate from the server with HydrationBoundary.
  • Persist the cache for offline-first apps (persistQueryClient) and retry with backoff.

Global client state patterns

  • Redux Toolkit: strong conventions, devtools, middleware, RTK Query; good for large teams with complex flows.
  • Zustand / Jotai / Valtio: minimal API, selector-based subscriptions, great for 3D apps where state changes fast.
  • Whatever you pick: normalize relational data (byId maps), keep reducers pure, and keep side effects out of them.

Architecture for scale

Feature-sliced structure and boundaries

Enforce boundaries with lint rules (eslint-plugin-boundaries, dependency-cruiser, Nx module boundaries) so the architecture survives team growth.

Patterns that keep components simple

  • Custom hooks as the service layer: useCheckout() encapsulates queries, mutations, derived data; the component only renders.
  • Presentational vs container: pure, prop-driven UI components are easy to test and put in Storybook.
  • Dependency injection via context for API clients, feature flags and analytics, so tests and stories can swap them.
  • Error handling strategy: error boundaries per region, typed error results in the data layer, user-friendly messages, and reporting to Sentry.
  • Feature flags (LaunchDarkly, Unleash, PostHog) to ship dark and roll out gradually.
  • Internationalization (i18next, Format.js) and Intl from day one if you may need it; forms via React Hook Form + Zod resolver.

Micro-frontends and monorepos (know when you don't need them)

Most teams are better served by a modular monolith or a monorepo (pnpm workspaces + Turborepo/Nx) sharing a UI package, config and types. Micro-frontends (Module Federation, single-spa) solve organizational scaling problems at high operational cost; adopt them only with that problem.

Exercises

  1. Take Project 3 and classify every piece of state using the taxonomy. Move anything misplaced (server data in Redux, filters in useState) to the right home.
  2. Implement optimistic updates with rollback for add/toggle/delete in TanStack Query. Add tests simulating a failing server.
  3. Model a checkout wizard with a state machine; generate a diagram of it (XState visualizer or a hand-drawn graph) and write tests for every transition.
  4. Rebuild a context-based store as a Zustand store with selectors; use the React Profiler to show the render count difference under rapid updates.
  5. Restructure an app into features with public index.ts APIs and enforce boundaries with a lint rule that fails CI.
  6. Set up a pnpm monorepo with apps/web, apps/api and packages/ui, packages/schemas shared (Zod), with Turborepo caching.

Checkpoint

Why not store fetched data in Redux/Zustand?Server data needs caching, deduplication, background refresh, invalidation and retries, which a query library provides. Copying it into a global store means re-implementing those features and keeping two sources of truth in sync.
When do you need a state machine?When behavior depends on a mode with legal and illegal transitions (wizards, uploads, media, auth), especially when boolean flags are multiplying.
